3기와 4기는 URL만 나누는 것으로 충분하지 않다. 모든 참가자, 인증, 댓글, 배너, 응원글, 응원 상자 데이터에는 서버가 결정한 `season_id`가 있어야 한다. 클라이언트가 제출한 시즌 값만 믿지 않고, 요청 경로와 활성 시즌 설정을 서버에서 다시 확인한다.

### 3기 동결 원칙

1. 기존 DB와 private Storage 객체를 각각 백업한다.
2. 참가자 수, 인증 레코드 수, 날짜별 인증 수, 누적 거리·시간을 기준값으로 저장한다.
3. 모든 기존 참가자와 인증 기록에 3기 시즌을 백필한다.
4. 백필 전후 기준값을 대조하고 시즌 스냅샷과 SHA-256 해시를 남긴다.
5. 3기를 `archived` 상태로 전환한다.
6. 일반 UI와 API뿐 아니라 PostgreSQL trigger에서도 3기 update/delete를 거부한다.
7. 정정이 꼭 필요한 경우에는 원본을 덮어쓰지 않고 운영자·사유·변경 전후 값을 감사 로그로 남기는 별도 절차를 사용한다.

최신 스키마는 운영 데이터의 관리자 `user_id` FK를 `ON DELETE RESTRICT`로 바꿔 Supabase Auth 계정의 실수 삭제가 3기·4기 참가자와 인증 기록을 연쇄 삭제하지 못하게 한다. 장기적으로 시즌 데이터 소유권을 관리자 계정과 분리하고, 실제 DB에 제약이 반영됐는지 운영 전 점검한다.

## 2. 이용자 구분과 가능한 기능

### 로그인하지 않은 방문자

- 3기·4기 공개 대시보드를 조회할 수 있다.
- 4기 댓글을 랜덤 익명 닉네임으로 남길 수 있다.
- 오늘의 운세를 확인할 수 없다.
- 오늘의 응원 상자를 열 수 없다.
- 인증 기록, 크루프로필, 운영 데이터를 직접 생성·수정·삭제할 수 없다.

### 카카오 로그인 이용자

- 공통 대시보드를 조회할 수 있다.
- Kakao가 제공한 프로필 닉네임으로 댓글과 답글을 남길 수 있고, 운영자가 확인한 표시명으로 바꾸면 이후 화면에 그 이름을 사용한다.
- 크루 승인이나 오늘 인증 없이 오늘의 운세를 확인할 수 있다.
- 운영자가 4기 참가자로 승인했고 오늘 인증이 완료된 경우에만 하루 한 번 오늘의 응원 상자를 열 수 있다.
- 교정운동 신청 메뉴를 볼 수 있으며, 건강 관련 정보 제출은 운영자가 4기 참가자 연결을 승인한 뒤에만 가능하다.
- 인증 등록·OCR·크루 관리 권한은 갖지 않는다. 현재 저장소의 개인 기록 입력·개인 OCR 경로는 이전 구현이므로 4기 운영 공개 전 UI와 API 모두에서 차단하거나 관리자 전용으로 전환한다.

카카오 프로필 닉네임은 법적 실명 확인값이 아니다. 운영자가 크루 명단과 대조해 정한 이름도 `운영자 확인 표시명`으로 표현하며, 별도의 본인확인 서비스 없이 `실명 인증`으로 표시하지 않는다. 로그인 댓글은 서버가 Kakao 세션의 프로필 닉네임 또는 운영자 override를 선택하며, 댓글 요청 본문이 보낸 작성자명을 신뢰하지 않는다.

### 승인된 4기 참가자

- 카카오 계정과 4기 시즌 참가자가 운영자에 의해 명시적으로 연결돼야 한다.
- 이름 유사도나 사용자 수정 가능 metadata만으로 자동 승인하지 않는다.
- 승인 해제 즉시 신규 응원 상자 개봉을 차단한다. 로그인 댓글은 Kakao 프로필 닉네임으로 유지하되 운영자 확인 배지를 제거한다.
- 인증 상태가 사후 반려되더라도 이미 지급된 응원 문구를 유지할지는 `[운영 전 확정 필요]`이다.

### 운영자

- 지정된 관리자 계정의 이메일 인증번호와 추가 서명 세션을 모두 통과해야 한다.
- `/admin`의 인증, 크루프로필, 응원글, 배너, 댓글, 교정운동 탭을 사용한다.
- 인증 OCR 결과를 검수하고 최종 인증 상태를 결정한다.
- 카카오 계정과 크루를 직접 확인해 승인·해제하고 운영자 확인 표시명을 관리한다.
- 댓글 숨김·복구·삭제, 더미데이터 제거, 시즌 동결 같은 중요한 작업은 감사 로그를 남긴다.
- 교정운동 신청의 민감정보는 일정 조율 담당자에게만 최소 권한으로 열람시키고, 단건 상세 열람은 신청 ID·운영자 ID·시각만 감사 로그에 남긴다. 상태 변경·일정 확정·삭제도 운영 감사 대상으로 관리하며 원문은 어떤 감사 로그에도 복제하지 않는다.
- 교정운동 일정 생성·변경, 신청 상태·확정 일정·신청자 안내 변경, 회원 취소와 운영자 삭제는 DB 트랜잭션 안에서 감사 행과 함께 처리한다. 감사 행에는 대상 UUID, 처리자 UUID, 역할, 동작, 변경된 필드명과 상태 전이만 저장하고 통증·병원·추가 메모 원문과 일정 값은 복제하지 않는다.

운영자 권한은 하드코딩된 이메일만으로 최종 결정하지 않고 `app_admins`와 같은 서버 관리 테이블에서 활성 상태와 역할을 확인하는 구조로 이전한다. 관리자 OTP 요청·검증에는 서버리스 인스턴스가 공유하는 지속형 rate limit을 적용한다.

## 3. 표시명과 댓글 운영

### 로그인 댓글

- 작성자명은 클라이언트 요청 본문에서 받지 않는다.
- Supabase `user_metadata`는 이용자가 수정할 수 있으므로 운영자 확인 이름이나 권한 판정에 사용하지 않는다.
- 카카오가 제공한 닉네임은 운영자 override가 없을 때 로그인 댓글 작성자명으로 사용한다.
- 공개 작성자명은 서버가 인증 세션에서 읽은 Kakao 닉네임 또는 서버 전용 운영자 override로 결정한다.
- 댓글에는 작성 당시 서버가 결정한 표시명을 스냅샷으로 남기고, 운영자 이름 변경은 이후 새 댓글부터 적용한다. 과거 댓글 이름 정정이 필요하면 별도 감사 절차로 처리한다.

### 익명 댓글

- 서버가 랜덤 닉네임을 배정하며 방문자가 임의의 실명이나 타인 이름을 작성자명으로 제출할 수 없게 한다.
- 서버가 충분히 긴 랜덤 게스트 토큰을 HttpOnly, Secure, SameSite=Lax 쿠키로 발급한다.
- DB에는 원본 토큰을 저장하지 않고 256비트 랜덤 토큰의 SHA-256 actor key만 저장한다. 원본 토큰은 HttpOnly 쿠키 밖으로 노출하지 않는다.
- 로그인 이용자는 익명 모드를 선택할 수 없다.
- 댓글·답글은 1자 이상 150자 이하로 제한하고, 서버와 DB 양쪽에서 검사한다.
- 제어문자를 제거하고 Unicode를 정규화하며 사용자 본문을 HTML로 실행하지 않는다.
- 댓글·답글·반응 API에는 동일 출처 검사, 지속형 rate limit, 스팸 방지, 반복 요청 방지를 적용한다.

### 댓글 상태와 조치

- 댓글 상태는 최소 `visible`, `hidden`, `deleted`로 구분한다.
- 운영자는 신고 또는 정책 위반 댓글을 우선 숨기고 사유를 기록한 뒤 복구 또는 삭제할 수 있다.
- 작성자 삭제 기능과 운영 문의를 통한 삭제 요청 절차를 제공한다.
- 삭제된 댓글 본문은 운영 화면에서도 일반 조회할 수 없게 하며, 필요한 최소 감사 정보만 별도 보관한다.

Hello 2027 공개 댓글은 Supabase 테이블을 사용하는 서버 API와 `/admin` 관리 화면에 연결돼 있다. 브라우저 IndexedDB는 개발용 `/poc`의 운영 원본으로 사용하지 않는다. 다만 운영 DB에 스키마·RLS·grants를 적용하고 삭제·복구·남용 방지를 실계정으로 검증한 뒤 `HELLO_2027_COMMENTS_LIVE=true`를 명시하기 전에는 더미 댓글 읽기 전용으로 유지한다. 플래그가 없거나 `true`가 아니면 댓글·답글·반응 쓰기는 실패-폐쇄된다.

## 4. 오늘의 운세와 응원 상자

### 오늘의 운세

- 유효한 Kakao 로그인이면 크루 승인이나 인증 여부와 관계없이 볼 수 있다.
- Asia/Seoul 날짜와 인증된 Supabase 사용자 ID를 운세 전용 서버 비밀값으로 HMAC해 하루 동안 같은 결과를 제공한다.
- 사용자 ID, HMAC 입력·digest, 비밀값은 응답이나 로그에 남기지 않는다.
- 운세 결과는 별도 DB에 저장하지 않으며 날짜가 바뀌면 다시 계산한다. 따라서 운세 때문에 추가되는 개인정보 보관은 없다.
- 운세는 오락용 응원 메시지이며 건강·재정·법률 또는 중요한 결정을 위한 예측으로 제공하지 않는다.
- `DAILY_FORTUNE_SECRET`은 32바이트 이상의 별도 난수값으로 배포 비밀 저장소에만 두고 관리자·Supabase·Kakao 비밀값과 재사용하지 않는다.

### 오늘의 응원 상자

응원 상자는 아래 조건을 서버에서 매 요청마다 다시 확인한다.

1. 유효한 Supabase 세션의 Kakao provider 로그인인가.
2. 해당 계정이 활성 4기 시즌 참가자와 운영자 승인 상태로 연결돼 있는가.
3. Asia/Seoul 기준 오늘 날짜의 인증이 `certified`인가.
4. 같은 시즌 참가자와 인증일에 이미 지급된 결과가 없는가.
5. 서버 전용 `FOURTH_GIFT_BOX_LIVE` 운영 플래그가 명시적으로 `true`인가.

브라우저가 보낸 참가자 ID, 인증 상태, 날짜, 상품 ID를 권한 근거로 신뢰하지 않는다. 랜덤 선택은 서버에서 수행하고 `UNIQUE(season_id, season_participant_id, record_date)` 제약으로 동시 클릭과 재요청에도 한 번만 지급한다. 지급 결과에는 당시 문구를 스냅샷으로 저장해 이후 상품 문구 수정이 과거 결과를 바꾸지 않게 한다.

현재 메시지형 MVP는 Kakao provider 재검증, `participant_accounts.season_key = '4th'`, `auth_user_id` 소유자 조건, 서버 전용 오픈 플래그, 4기 운영 기간(2026-09-23~2026-12-31) 검증을 적용한다. `FOURTH_GIFT_BOX_LIVE`가 없거나 `true`가 아니면 기간 중에도 지급은 실패-폐쇄된다. 기존 승인 행은 자동으로 4기에 포함하지 않고 운영자가 4기 연결을 다시 저장해야 한다. 정식 시즌 모델에서는 참가자·인증 레코드에도 `season_id`를 추가해 4기 소속을 DB 외래키로 검증한다.

## 4-1. 교정운동 신청과 일정 조율

교정운동 신청은 의료 진단·치료·처방 또는 응급 대응 서비스가 아니다. 화면과 운영자 도구에서 이 한계를 명확히 알리고, 응급하거나 급격히 악화된 증상은 신청 처리를 기다리지 말고 119 또는 의료기관을 이용하도록 안내한다. 서비스는 질환명, 진단서, 주민등록번호, 보험정보, 의료영상·사진을 요구하지 않는다.

### 이용 흐름

1. 운영자가 `/admin?tab=corrective-exercise`에서 신청 가능한 날짜·시간, 정원, 공개 메모를 만든다.
2. Kakao 로그인과 운영자 승인 참가자 연결을 모두 확인한 이용자에게만 신청 폼을 연다.
3. 이용자는 가능한 일정 하나, 불편한 부위, 불편이 발생하는 상황, 병원 이용 상태, 선택 메모를 작성한다.
4. 건강 관련 민감정보 수집·이용 동의를 다른 동의와 구분해 명시적으로 받는다.
5. 서버는 슬롯 활성 여부·미래 날짜·잔여 정원·중복 활성 신청을 트랜잭션에서 다시 확인한다.
6. 운영자는 접수, 확인 중, 일정 제안, 확정, 완료, 취소·거절 상태와 확정 일정을 관리한다.
7. 이용자는 본인 신청 상태만 보고, 확정 전 활성 신청을 취소할 수 있다.
8. 삭제 요청을 확인한 운영자는 추가 OTP 세션이 유지된 `/admin`에서 2단계 확인 후 신청을 즉시 삭제한다. 삭제 후에도 건강 문진 원문은 남기지 않고 최소 변경 감사 행만 365일 이내 보관한다.

### 민감정보 동의와 보관

- 동의 버전 `2026-09-04-v1`은 수집 항목(크루 식별, 희망 일정, 통증 부위·발생 상황, 병원 이용 상태, 선택 메모), 목적(교정운동 상담 준비와 일정 조율), 보유기간, 거부권과 거부 시 신청 불가를 함께 표시한다.
- 신청 데이터는 접수 시점부터 최대 180일까지만 보관한다. 완료·취소·거절 시에는 해당 시점부터 90일과 기존 만료일 중 더 이른 날에 파기한다. 이용자가 더 이른 삭제를 요청하면 법적 보존 근거가 없는 한 지체 없이 처리한다.
- `retention_until`이 지난 신청과 열람·변경 감사 로그를 정기 삭제하는 작업은 `docs/migrations/2026-09-04-corrective-exercise-retention-cron.sql`로 명시적으로 연결하고, 백업에 남는 기간과 복원 후 재삭제 절차를 별도로 확인한다.
- 건강 관련 본문은 공개 대시보드, 브라우저 저장소, 분석 이벤트, 일반 오류 로그에 포함하지 않는다. 데이터베이스의 `anon`, 일반 `authenticated`, `PUBLIC` 역할에는 테이블과 관련 함수 권한을 주지 않고, 본인 확인·관리자 추가 인증을 거친 서버 경로만 service-role로 접근한다.
- DB의 `admin_note` 컬럼은 이름과 달리 **신청자 본인에게 공개되는 안내문**이다. 내부 판단·진단·운영 메모를 입력하지 않으며, 관리자 화면에서도 `신청자 안내`로 표시한다. 내부 메모가 필요해지면 이 컬럼을 재사용하지 않고 별도 비공개 테이블·권한·보관기간을 설계한 뒤 도입한다.
- 서버 전용 `CORRECTIVE_EXERCISE_LIVE`가 정확히 `true`가 아니면 회원 API는 신청 일정과 기존 신청 본문을 조회하지 않고 준비 상태만 반환하며 POST를 거부한다. 관리자 준비 화면은 계속 접근할 수 있다. 마이그레이션·Cron·문의처·권한 실검증 전에는 이 값을 켜지 않는다.
- 운영 화면은 민감정보임을 상시 표시하고, 상담·일정 조율에 필요한 담당자 외 열람을 금지한다. 화면 캡처·메신저 재전송·로컬 파일 다운로드를 기본 운영 흐름으로 사용하지 않는다.

건강정보는 개인정보 보호법상 민감정보이므로 다른 개인정보 처리 동의와 별도로 받아야 한다. 실제 운영 공개 전에는 운영 주체, 담당자, 삭제 요청 창구, Supabase 리전·백업 잔존기간과 위탁 사항을 확정해 개인정보처리방침에도 같은 내용으로 반영한다.

## 6. Supabase 저장·권한·백업 정책

### 데이터 위치와 위탁

- Supabase 프로젝트는 하나의 기본 리전에 배치되므로 실제 리전과 데이터 처리 위치를 운영정책과 개인정보처리방침에 명시한다: `[운영 전 확정 필요]`.
- 한국 사용자 중심 서비스의 성능을 위해 새 프로젝트라면 Seoul 리전을 우선 검토하되, 지역 선택만으로 법률 준수가 자동 보장되는 것은 아니다.
- Supabase 및 그 하위 처리자 관련 고지는 실제 계약·프로젝트 설정을 기준으로 확정한다.

### RLS와 서버 권한

- 외부에 노출되는 모든 public 스키마 테이블에 RLS를 활성화한다.
- 공개 화면도 허용된 필드만 반환하는 Next 서버 API를 사용한다.
- `anon`과 일반 `authenticated` 역할에는 참가자, 인증, 계정 연결, 선물상자, 운영 데이터의 직접 insert/update/delete 권한을 부여하지 않는다.
- service-role 또는 secret key는 서버 전용 환경변수로만 저장하며 브라우저 코드, 로그, 채팅, 저장소에 노출하지 않는다.
- Supabase anon/publishable key는 공개 사용을 전제로 한 식별값이며 숨김 대상이 아니다. RLS와 grants를 실제 보안 경계로 사용한다.
- Kakao Client Secret, service-role, 관리자 세션 비밀값, 운세 HMAC 비밀값은 서로 재사용하지 않고 `NEXT_PUBLIC_*`에 넣지 않는다.
- service role은 RLS를 우회하므로 모든 서버 API에서 역할·시즌·소유권·상태를 다시 검사하고 DB 제약과 trigger를 함께 사용한다.
- 배포 전에 Supabase Security Advisor와 allow/deny RLS 테스트를 실행한다.

### Storage

- 인증 원본과 크루 관련 미디어는 용도별 private bucket에 저장한다.
- 공개 화면에는 허용된 변환본 또는 짧은 만료시간의 서명 URL만 제공한다.
- 업로드 파일은 확장자나 MIME 문자열만 믿지 않고 실제 디코딩·재인코딩·EXIF 제거 절차를 적용한다.
- DB 백업에는 Storage 객체 파일 자체가 포함되지 않으므로 DB와 Storage를 각각 백업하고 복구 시험을 수행한다.

### 백업과 삭제 잔존

Supabase의 실제 자동 DB 백업 기간은 사용 요금제에 따라 다르므로 운영 콘솔에서 확인해 기록한다: `[운영 전 확정 필요]`. 삭제된 개인정보가 제한된 기간 백업에 남을 수 있다면 그 기간과 접근 제한을 고지한다. 백업을 복원할 때 이미 처리된 삭제·연결 해제 요청이 되살아나지 않도록 삭제 처리 목록을 다시 적용하는 복구 절차를 마련한다.

## 7. Kakao 로그인과 연결 해제

### TWTT 전용 Kakao 앱 설정

- 앱 이름, 아이콘, 운영 주체를 실제 서비스와 일치하게 등록한다.
- 기본/Web 도메인: `https://xn--220bw61afob.kro.kr`
- Kakao Login과 Client Secret을 활성화한다.
- Kakao Redirect URI에는 Supabase Dashboard에 표시되는 `https://<project-ref>.supabase.co/auth/v1/callback`을 정확히 등록한다.
- Supabase Site URL은 `https://xn--220bw61afob.kro.kr`로 설정한다.
- Supabase Redirect Allow List에는 `https://xn--220bw61afob.kro.kr/api/auth/callback`을 정확히 등록하고, 운영 환경에서 과도한 wildcard를 사용하지 않는다.
- `profile_nickname`만 우선 요청하고 프로필 이미지·이메일은 실제 기능에 필요할 때만 추가한다.
- 이메일을 요청하지 않는 경우 Supabase Kakao provider의 `Allow users without an email`을 활성화한다.
- Kakao REST API key와 Client Secret은 Supabase provider 설정에 저장한다. 별도 Kakao API를 서버에서 직접 호출하지 않는 한 브라우저 또는 일반 공개 환경변수에 넣지 않는다.
- Kakao 앱 Owner 계정은 강한 인증수단으로 보호하고 불필요한 팀원을 제거한다.

### 세션

- Supabase SSR PKCE 쿠키 흐름을 사용한다.
- Next.js Proxy에서 공식 권장 방식으로 만료 토큰을 갱신하고 인증 응답을 `private, no-store`로 처리한다.
- 민감한 응원 상자·관리자 작업은 최신 사용자 상태와 승인 상태를 서버에서 확인한다.
- 로그아웃은 TWTT 세션 종료이며 Kakao 계정 자체의 전체 로그아웃이나 연결 해제와 구분해 안내한다.

### 연결 해제와 탈퇴

- 서비스 안에서 계정 삭제·연결 해제 요청 경로를 제공한다.
- Kakao 계정 관리 화면에서 외부 연결 해제가 발생하는 경우를 받기 위해 Kakao unlink webhook을 운영 전 구성한다.
- webhook은 Kakao가 정의한 인증값과 앱 ID를 검증하고, 민감한 헤더나 사용자 정보를 로그에 남기지 않는다.
- 유효한 연결 해제 이벤트를 받으면 Kakao user ID, 닉네임, 계정 연결을 삭제하고 활성 세션·신규 기능 권한을 해제한다.
- 최신 DB 스키마는 Kakao 반응에 서버 전용 `auth_user_id`를 연결하고, Auth 사용자 삭제 직전에 댓글을 `탈퇴한 이용자`로 비식별화하며 해당 반응을 제거해 FK와 작성자 일관성을 함께 유지한다. Kakao 쪽 연결 해제만 발생하고 Supabase Auth 행이 남는 경우에는 이 trigger가 실행되지 않으므로 unlink webhook이 반드시 Auth 삭제 또는 같은 비식별화 절차를 완료해야 한다. 운영 전에는 `actor_key LIKE 'user:%' AND auth_user_id IS NULL`인 식별 불가 레거시 반응이 0건인지 확인한다.
- 시즌 기록을 별도 보존할 정당한 목적과 동의가 있는 경우에도 Kakao 식별자와 분리하고 표시명을 익명화할지 여부를 사전 고지한 정책에 따라 처리한다.
- 연결 해제·삭제 처리에 실패해도 webhook에는 Kakao 재시도 규격에 맞는 응답을 보내고 내부 재처리 큐와 감사 로그로 완료 여부를 추적한다.

## 8. 4기 더미데이터와 오픈 전 안내

4기 공개 전 더미데이터는 실제 데이터와 섞이지 않도록 4기 `draft` 시즌 안에서 `is_demo` 또는 명시적인 seed 식별자로 관리한다.

### 더미데이터 제거 절차

1. 4기 운영 시작 시각과 제거 담당자를 확정한다.
2. 삭제 대상이 4기 draft의 명시적인 더미데이터인지 읽기 전용 쿼리로 확인한다.
3. 실사용 카카오 계정, 실제 댓글, 실제 인증, 3기 데이터가 대상에 포함되지 않는지 검증한다.
4. 제거 전 레코드 수와 식별자 목록을 보관한다.
5. 인증, 댓글, 응원 상자, 크루프로필, 배너, 응원글 순서로 참조 관계를 확인하며 제거한다.
6. 더미 레코드가 0건인지, 3기 기준값이 그대로인지, 4기 실데이터가 보존됐는지 다시 확인한다.
7. 공개 캐시를 무효화하고 모바일·웹 화면을 점검한다.
8. 담당자, 시각, 제거 건수, 검증 결과를 감사 로그에 남긴다.

운영 시작 전 4기 페이지에는 `9월 중순에 셔터 올립니다!` 안내를 표시한다. `오늘 그만보기`는 브라우저의 Asia/Seoul 날짜가 바뀔 때까지만 숨김 상태를 유지하며, 필수 공지나 약관 동의를 대신하지 않는다.

## 9. 보안사고와 장애 대응

### 탐지와 초기 대응

1. 의심 활동의 요청 ID, 시각, 영향 API와 데이터 범위를 확인한다.
2. 영향받은 댓글 작성, 응원 상자, 업로드 또는 관리자 기능을 최소 범위로 일시 중단한다.
3. 노출 가능성이 있는 Supabase secret/service-role key, Kakao Client Secret·Admin key, 관리자 세션 비밀값을 즉시 폐기·교체한다.
4. 로그에 비밀값이나 개인정보가 포함됐다면 접근을 제한하고 별도 사고 범위에 포함한다.
5. 데이터 변경 전후 값과 삭제 이벤트를 보존하되 불필요한 개인정보 복제는 만들지 않는다.

### 조사·복구·고지

- Supabase 로그, Kakao 설정 변경 이력, 관리자 감사 로그, 배포 이력을 대조한다.
- 정상 백업과 Storage 사본으로 복구할 때 시즌 동결과 기존 삭제 요청을 다시 적용한다.
- 운영 주체는 영향받은 정보와 이용자, 오남용 가능성, 적용 법률을 검토해 관계기관·이용자 고지 필요성과 시점을 결정한다. 구체 기한과 절차는 `[운영 전 확정 필요]`이다.
- 사고 종료 후 원인, 영향, 조치, 재발 방지, 키 교체 완료, 사용자 안내를 문서화한다.

- [ ] 운영자 삭제가 최신 `updated_at` 일치와 2단계 확인을 요구하고, 삭제 뒤 신청 원문이 조회되지 않는다.
- [ ] 회원에게 공개되는 `admin_note`에 기존 내부 메모가 남아 있지 않은지 운영 데이터 전체를 검토했다.
- [ ] 비활성·과거·마감 슬롯, 중복 활성 신청, 동시 마지막 자리 신청이 서버와 DB에서 거부된다.
- [ ] `anon`, `authenticated`, `PUBLIC` 역할의 신청·슬롯 테이블 및 함수 직접 접근이 거부된다.
- [ ] 만료 신청 정기 파기 작업과 백업 복원 후 재삭제 절차를 검증했다.
- [ ] 민감정보가 오류 로그·분석 이벤트·공개 응답·브라우저 저장소에 남지 않는지 확인했다.
- [ ] 위 점검을 모두 마친 뒤에만 `CORRECTIVE_EXERCISE_LIVE=true`를 배포 환경에 설정했다.

### Supabase와 배포 보안

- [ ] 모든 노출 테이블에 RLS가 켜져 있고 grants와 policies를 함께 검증했다.
- [ ] `anon`·일반 `authenticated`의 민감 테이블 직접 쓰기가 거부된다.
- [ ] service-role, Kakao 비밀값, 운세 HMAC 비밀값, Gemini 키가 서버 비밀 저장소에만 있고 서로 재사용되지 않는다.
- [ ] Supabase Security Advisor와 RLS allow/deny 테스트를 통과했다.
- [ ] private Storage 정책, 서명 URL, 이미지 검증과 EXIF 제거를 확인했다.
- [ ] DB와 Storage를 각각 백업하고 실제 복원 시험을 완료했다.
- [ ] 보안 헤더, 오류 응답, 캐시의 사용자 간 데이터 혼합 여부를 점검했다.
- [ ] 320·360·390·412px 모바일과 주요 웹 너비, 저속 네트워크에서 첫 화면과 로그인 동선을 확인했다.

체크리스트를 모두 충족하기 전에는 4기 오픈 전 안내를 제거하지 않는다.

## 11. 현재 구현 상태와 배포 제한

2026-09-04 저장소 기준으로 공통 진입 선택 화면, 서버 OAuth 시작, 헤더의 로그인·로그아웃, Kakao provider 판정, Kakao identity의 프로필 이름과 운영자 표시명 override, 인증 없이 보는 서버 HMAC 운세, 4기 시즌 키가 있는 계정 승인 연결, 4기 운영 기간을 검사하는 메시지형 응원 상자 MVP, 관리자 OTP·탭 UI, Supabase 세션 갱신 Proxy가 구현돼 있다. 개인 인증·OCR API는 4기 개인 계정에 열리지 않도록 403으로 차단했다. 3기 공개 화면과 리포트는 2026-05-05~08-12 공개 기록을 식별자 제거 후 고정한 스냅샷만 읽는다. 또한 응원글·배너·크루 자기소개 공개 API, 관리자 콘텐츠 CRUD, 공개 댓글·답글·반응 API, 관리자 숨김·복구·비식별 삭제, 교정운동 신청·운영 가능 일정·관리자 상태 조율 UI와 서버 API가 구현됐다. 댓글 쓰기는 운영 SQL과 실계정 검증 후 `HELLO_2027_COMMENTS_LIVE=true`로 전환하기 전까지 더미 댓글 읽기 전용이다. 교정운동 신청은 운영 SQL·Cron·동의 문구·본인 및 관리자 권한을 검증하고 `CORRECTIVE_EXERCISE_LIVE=true`로 전환하기 전까지 실패-폐쇄된다.

다음 항목은 정식 운영 전 필수 작업이다.

- TWTT Kakao 앱·Supabase provider·운영 redirect 설정과 실제 계정 검증
- 운영 Supabase에 `docs/supabase-schema.sql`과 `docs/supabase-security-hardening.sql` 적용 및 grants/RLS 검증
- 3기·4기 `seasons`, `season_participants` 도입, 운영 DB의 3기 trigger 동결과 관리자 Auth 소유권 분리
- 새 콘텐츠·댓글 테이블과 RLS/grants를 운영 Supabase에 적용하고 실계정으로 검증
- 댓글·답글·반응의 서버리스 공유 지속형 rate limit·스팸 방지와 관리자 감사 로그
- Kakao unlink webhook과 외부 연결 해제 후 식별 정보 삭제 처리
- 실제 보관기간·삭제 처리·Supabase 리전 확정
- 교정운동 민감정보 동의 문구 확정, 운영 SQL 적용, 만료 데이터 파기 스케줄과 관리자 열람 감사 로그 연결
- 4기 더미데이터 제거 및 롤백·DB와 Storage 복구 시험

이 제한이 남아 있는 동안 더미데이터가 있는 4기 화면은 오픈 전 안내가 적용된 사전 공개 화면으로만 운영한다.
