## 1. 서비스 주소와 시즌 분리

| 구분 | 주소 | 운영 원칙 |
| --- | --- | --- |
| TWTT 3기 | `https://xn--220bw61afob.kro.kr/3th` | 기존 기록을 읽기 전용으로 제공한다. |
| TWTT 4기 | `https://xn--220bw61afob.kro.kr/4th` | 4기 전용 시즌·참가자·콘텐츠·인증 데이터만 제공한다. |
| 운영 어드민 | `https://xn--220bw61afob.kro.kr/admin` | 같은 주소를 유지하되 시즌 선택과 권한 검사를 거친다. |

3기와 4기는 URL만 나누는 것으로 충분하지 않다. 모든 참가자, 인증, 댓글, 배너, 응원글, 응원 상자 데이터에는 서버가 결정한 `season_id`가 있어야 한다. 클라이언트가 제출한 시즌 값만 믿지 않고, 요청 경로와 활성 시즌 설정을 서버에서 다시 확인한다.

### 3기 동결 원칙

1. 기존 DB와 private Storage 객체를 각각 백업한다.
2. 참가자 수, 인증 레코드 수, 날짜별 인증 수, 누적 거리·시간을 기준값으로 저장한다.
3. 모든 기존 참가자와 인증 기록에 3기 시즌을 백필한다.
4. 백필 전후 기준값을 대조하고 시즌 스냅샷과 SHA-256 해시를 남긴다.
5. 3기를 `archived` 상태로 전환한다.
6. 일반 UI와 API뿐 아니라 PostgreSQL trigger에서도 3기 update/delete를 거부한다.
7. 정정이 꼭 필요한 경우에는 원본을 덮어쓰지 않고 운영자·사유·변경 전후 값을 감사 로그로 남기는 별도 절차를 사용한다.

관리자 Supabase Auth 계정을 삭제해도 3기 참가자·인증 기록이 연쇄 삭제되지 않도록, 시즌 데이터의 소유권을 관리자 계정과 분리하고 기존 `ON DELETE CASCADE` 관계를 운영 전 점검한다.

## 2. 이용자 구분과 가능한 기능

### 로그인하지 않은 방문자

- 3기·4기 공개 대시보드를 조회할 수 있다.
- 4기 댓글을 랜덤 익명 닉네임으로 남길 수 있다.
- 오늘의 응원 상자를 열 수 없다.
- 인증 기록, 크루프로필, 운영 데이터를 직접 생성·수정·삭제할 수 없다.

### 카카오 로그인 이용자

- 공통 대시보드를 조회할 수 있다.
- 운영자가 확인한 표시명으로 댓글과 답글을 남길 수 있다.
- 운영자가 4기 참가자로 승인했고 오늘 인증이 완료된 경우에만 하루 한 번 오늘의 응원 상자를 열 수 있다.
- 인증 등록·OCR·크루 관리 권한은 갖지 않는다. 현재 저장소의 개인 기록 입력·개인 OCR 경로는 이전 구현이므로 4기 운영 공개 전 UI와 API 모두에서 차단하거나 관리자 전용으로 전환한다.

카카오 프로필 닉네임은 법적 실명 확인값이 아니다. 운영자가 크루 명단과 대조해 정한 이름도 `운영자 확인 표시명`으로 표현하며, 별도의 본인확인 서비스 없이 `실명 인증`으로 표시하지 않는다. 운영자 확인 전에는 로그인 댓글 작성을 막고 `이름 확인 중` 상태를 안내하는 것을 기본 정책으로 한다.

### 승인된 4기 참가자

- 카카오 계정과 4기 시즌 참가자가 운영자에 의해 명시적으로 연결돼야 한다.
- 이름 유사도나 사용자 수정 가능 metadata만으로 자동 승인하지 않는다.
- 승인 해제 즉시 신규 응원 상자 개봉과 로그인 전용 댓글 작성을 차단한다.
- 인증 상태가 사후 반려되더라도 이미 지급된 응원 문구를 유지할지는 `[운영 전 확정 필요]`이다.

### 운영자

- 지정된 관리자 계정의 이메일 인증번호와 추가 서명 세션을 모두 통과해야 한다.
- `/admin`의 인증, 크루프로필, 응원글, 배너, 댓글 탭을 사용한다.
- 인증 OCR 결과를 검수하고 최종 인증 상태를 결정한다.
- 카카오 계정과 크루를 직접 확인해 승인·해제하고 운영자 확인 표시명을 관리한다.
- 댓글 숨김·복구·삭제, 더미데이터 제거, 시즌 동결 같은 중요한 작업은 감사 로그를 남긴다.

운영자 권한은 하드코딩된 이메일만으로 최종 결정하지 않고 `app_admins`와 같은 서버 관리 테이블에서 활성 상태와 역할을 확인하는 구조로 이전한다. 관리자 OTP 요청·검증에는 서버리스 인스턴스가 공유하는 지속형 rate limit을 적용한다.

## 3. 표시명과 댓글 운영

### 로그인 댓글

- 작성자명은 클라이언트 요청 본문에서 받지 않는다.
- Supabase `user_metadata`는 이용자가 수정할 수 있으므로 운영자 확인 이름이나 권한 판정에 사용하지 않는다.
- 카카오가 제공한 닉네임은 운영자 참고용 스냅샷으로만 저장한다.
- 공개 작성자명은 서버 전용 회원 프로필의 운영자 확인 표시명으로 결정한다.
- 운영자가 이름을 수정하면 기존 댓글에도 최신 표시명을 적용하되, 감사 목적으로 작성 당시 이름 스냅샷과 변경 이력을 별도로 보관한다.

### 익명 댓글

- 서버가 랜덤 닉네임을 배정하며 방문자가 임의의 실명이나 타인 이름을 작성자명으로 제출할 수 없게 한다.
- 서버가 충분히 긴 랜덤 게스트 토큰을 HttpOnly, Secure, SameSite=Lax 쿠키로 발급한다.
- DB에는 원본 토큰을 저장하지 않고 서버 비밀값으로 만든 HMAC만 저장한다.
- 로그인 이용자는 익명 모드를 선택할 수 없다.
- 댓글·답글은 1자 이상 150자 이하로 제한하고, 서버와 DB 양쪽에서 검사한다.
- 제어문자를 제거하고 Unicode를 정규화하며 사용자 본문을 HTML로 실행하지 않는다.
- 댓글·답글·반응 API에는 동일 출처 검사, 지속형 rate limit, 스팸 방지, 반복 요청 방지를 적용한다.

### 댓글 상태와 조치

- 댓글 상태는 최소 `visible`, `hidden`, `deleted`로 구분한다.
- 운영자는 신고 또는 정책 위반 댓글을 우선 숨기고 사유를 기록한 뒤 복구 또는 삭제할 수 있다.
- 작성자 삭제 기능과 운영 문의를 통한 삭제 요청 절차를 제공한다.
- 삭제된 댓글 본문은 운영 화면에서도 일반 조회할 수 없게 하며, 필요한 최소 감사 정보만 별도 보관한다.

현재 Hello 2027 댓글은 브라우저 IndexedDB를 사용하는 개발용 구현이다. 서버 댓글 테이블·API·운영자 관리·삭제 절차가 연결되기 전에는 이를 운영 데이터 저장소로 취급하거나 production에 공개하지 않는다.

## 4. 오늘의 응원 상자

응원 상자는 아래 조건을 서버에서 매 요청마다 다시 확인한다.

1. 유효한 Supabase 세션의 Kakao provider 로그인인가.
2. 해당 계정이 활성 4기 시즌 참가자와 운영자 승인 상태로 연결돼 있는가.
3. Asia/Seoul 기준 오늘 날짜의 인증이 `certified`인가.
4. 같은 시즌 참가자와 인증일에 이미 지급된 결과가 없는가.

브라우저가 보낸 참가자 ID, 인증 상태, 날짜, 상품 ID를 권한 근거로 신뢰하지 않는다. 랜덤 선택은 서버에서 수행하고 `UNIQUE(season_id, season_participant_id, record_date)` 제약으로 동시 클릭과 재요청에도 한 번만 지급한다. 지급 결과에는 당시 문구를 스냅샷으로 저장해 이후 상품 문구 수정이 과거 결과를 바꾸지 않게 한다.

현재 메시지형 MVP는 Kakao provider 재검증, `auth_user_id` 소유자 조건, 시즌 키를 완성한 뒤 운영에 사용한다.

## 6. Supabase 저장·권한·백업 정책

### 데이터 위치와 위탁

- Supabase 프로젝트는 하나의 기본 리전에 배치되므로 실제 리전과 데이터 처리 위치를 운영정책과 개인정보처리방침에 명시한다: `[운영 전 확정 필요]`.
- 한국 사용자 중심 서비스의 성능을 위해 새 프로젝트라면 Seoul 리전을 우선 검토하되, 지역 선택만으로 법률 준수가 자동 보장되는 것은 아니다.
- Supabase 및 그 하위 처리자 관련 고지는 실제 계약·프로젝트 설정을 기준으로 확정한다.

### RLS와 서버 권한

- 외부에 노출되는 모든 public 스키마 테이블에 RLS를 활성화한다.
- 공개 화면도 허용된 필드만 반환하는 Next 서버 API를 사용한다.
- `anon`과 일반 `authenticated` 역할에는 참가자, 인증, 계정 연결, 선물상자, 운영 데이터의 직접 insert/update/delete 권한을 부여하지 않는다.
- service-role 또는 secret key는 서버 전용 환경변수로만 저장하며 브라우저 코드, 로그, 채팅, 저장소에 노출하지 않는다.
- service role은 RLS를 우회하므로 모든 서버 API에서 역할·시즌·소유권·상태를 다시 검사하고 DB 제약과 trigger를 함께 사용한다.
- 배포 전에 Supabase Security Advisor와 allow/deny RLS 테스트를 실행한다.

### Storage

- 인증 원본과 크루 관련 미디어는 용도별 private bucket에 저장한다.
- 공개 화면에는 허용된 변환본 또는 짧은 만료시간의 서명 URL만 제공한다.
- 업로드 파일은 확장자나 MIME 문자열만 믿지 않고 실제 디코딩·재인코딩·EXIF 제거 절차를 적용한다.
- DB 백업에는 Storage 객체 파일 자체가 포함되지 않으므로 DB와 Storage를 각각 백업하고 복구 시험을 수행한다.

### 백업과 삭제 잔존

Supabase의 실제 자동 DB 백업 기간은 사용 요금제에 따라 다르므로 운영 콘솔에서 확인해 기록한다: `[운영 전 확정 필요]`. 삭제된 개인정보가 제한된 기간 백업에 남을 수 있다면 그 기간과 접근 제한을 고지한다. 백업을 복원할 때 이미 처리된 삭제·연결 해제 요청이 되살아나지 않도록 삭제 처리 목록을 다시 적용하는 복구 절차를 마련한다.

## 7. Kakao 로그인과 연결 해제

### TWTT 전용 Kakao 앱 설정

- 앱 이름, 아이콘, 운영 주체를 실제 서비스와 일치하게 등록한다.
- 기본/Web 도메인: `https://xn--220bw61afob.kro.kr`
- Kakao Login과 Client Secret을 활성화한다.
- Kakao Redirect URI에는 Supabase Dashboard에 표시되는 `https://<project-ref>.supabase.co/auth/v1/callback`을 정확히 등록한다.
- Supabase Site URL은 `https://xn--220bw61afob.kro.kr`로 설정한다.
- Supabase Redirect Allow List에는 `https://xn--220bw61afob.kro.kr/api/auth/callback`을 정확히 등록하고, 운영 환경에서 과도한 wildcard를 사용하지 않는다.
- `profile_nickname`만 우선 요청하고 프로필 이미지·이메일은 실제 기능에 필요할 때만 추가한다.
- 이메일을 요청하지 않는 경우 Supabase Kakao provider의 `Allow users without an email`을 활성화한다.
- Kakao REST API key와 Client Secret은 Supabase provider 설정에 저장한다. 별도 Kakao API를 서버에서 직접 호출하지 않는 한 브라우저 또는 일반 공개 환경변수에 넣지 않는다.
- Kakao 앱 Owner 계정은 강한 인증수단으로 보호하고 불필요한 팀원을 제거한다.

### 세션

- Supabase SSR PKCE 쿠키 흐름을 사용한다.
- Next.js Proxy에서 공식 권장 방식으로 만료 토큰을 갱신하고 인증 응답을 `private, no-store`로 처리한다.
- 민감한 응원 상자·관리자 작업은 최신 사용자 상태와 승인 상태를 서버에서 확인한다.
- 로그아웃은 TWTT 세션 종료이며 Kakao 계정 자체의 전체 로그아웃이나 연결 해제와 구분해 안내한다.

### 연결 해제와 탈퇴

- 서비스 안에서 계정 삭제·연결 해제 요청 경로를 제공한다.
- Kakao 계정 관리 화면에서 외부 연결 해제가 발생하는 경우를 받기 위해 Kakao unlink webhook을 운영 전 구성한다.
- webhook은 Kakao가 정의한 인증값과 앱 ID를 검증하고, 민감한 헤더나 사용자 정보를 로그에 남기지 않는다.
- 유효한 연결 해제 이벤트를 받으면 Kakao user ID, 닉네임, 계정 연결을 삭제하고 활성 세션·신규 기능 권한을 해제한다.
- 시즌 기록을 별도 보존할 정당한 목적과 동의가 있는 경우에도 Kakao 식별자와 분리하고 표시명을 익명화할지 여부를 사전 고지한 정책에 따라 처리한다.
- 연결 해제·삭제 처리에 실패해도 webhook에는 Kakao 재시도 규격에 맞는 응답을 보내고 내부 재처리 큐와 감사 로그로 완료 여부를 추적한다.

## 8. 4기 더미데이터와 오픈 전 안내

4기 공개 전 더미데이터는 실제 데이터와 섞이지 않도록 4기 `draft` 시즌 안에서 `is_demo` 또는 명시적인 seed 식별자로 관리한다.

### 더미데이터 제거 절차

1. 4기 운영 시작 시각과 제거 담당자를 확정한다.
2. 삭제 대상이 4기 draft의 명시적인 더미데이터인지 읽기 전용 쿼리로 확인한다.
3. 실사용 카카오 계정, 실제 댓글, 실제 인증, 3기 데이터가 대상에 포함되지 않는지 검증한다.
4. 제거 전 레코드 수와 식별자 목록을 보관한다.
5. 인증, 댓글, 응원 상자, 크루프로필, 배너, 응원글 순서로 참조 관계를 확인하며 제거한다.
6. 더미 레코드가 0건인지, 3기 기준값이 그대로인지, 4기 실데이터가 보존됐는지 다시 확인한다.
7. 공개 캐시를 무효화하고 모바일·웹 화면을 점검한다.
8. 담당자, 시각, 제거 건수, 검증 결과를 감사 로그에 남긴다.

운영 시작 전 4기 페이지에는 `오픈 전입니다. 9월 중순에 셔터 올립니다` 안내를 표시한다. `오늘 그만보기`는 브라우저의 Asia/Seoul 날짜가 바뀔 때까지만 숨김 상태를 유지하며, 필수 공지나 약관 동의를 대신하지 않는다.

## 9. 보안사고와 장애 대응

### 탐지와 초기 대응

1. 의심 활동의 요청 ID, 시각, 영향 API와 데이터 범위를 확인한다.
2. 영향받은 댓글 작성, 응원 상자, 업로드 또는 관리자 기능을 최소 범위로 일시 중단한다.
3. 노출 가능성이 있는 Supabase secret/service-role key, Kakao Client Secret·Admin key, 관리자 세션 비밀값을 즉시 폐기·교체한다.
4. 로그에 비밀값이나 개인정보가 포함됐다면 접근을 제한하고 별도 사고 범위에 포함한다.
5. 데이터 변경 전후 값과 삭제 이벤트를 보존하되 불필요한 개인정보 복제는 만들지 않는다.

### 조사·복구·고지

- Supabase 로그, Kakao 설정 변경 이력, 관리자 감사 로그, 배포 이력을 대조한다.
- 정상 백업과 Storage 사본으로 복구할 때 시즌 동결과 기존 삭제 요청을 다시 적용한다.
- 운영 주체는 영향받은 정보와 이용자, 오남용 가능성, 적용 법률을 검토해 관계기관·이용자 고지 필요성과 시점을 결정한다. 구체 기한과 절차는 `[운영 전 확정 필요]`이다.
- 사고 종료 후 원인, 영향, 조치, 재발 방지, 키 교체 완료, 사용자 안내를 문서화한다.

- [ ] TWTT 전용 Kakao 앱의 이름·아이콘·운영 주체·도메인을 확인했다.
- [ ] Kakao Login, Client Secret, Redirect URI, 최소 동의항목을 설정했다.

- [ ] 운영·개인정보 문의 연락처를 확정했다.
- [ ] 실제 Supabase 리전, 요금제, DB 백업 기간을 정책에 반영했다.

### 인증과 권한

- [ ] SSR Proxy로 세션 갱신을 검증했다.
- [ ] 로그인 취소, 잘못된 redirect, 세션 만료, 로그아웃, 외부 연결 해제를 테스트했다.
- [ ] 비카카오·미승인·승인 해제 계정의 응원 상자 접근이 거부된다.
- [ ] 일반 카카오 사용자는 인증·OCR·크루·운영 API를 호출할 수 없다.
- [ ] 비관리자와 만료된 OTP 세션은 모든 관리자 API에서 차단된다.
- [ ] 관리자 OTP와 댓글에 지속형 rate limit이 적용됐다.

### 데이터와 시즌

- [ ] 3기 백업, 백필, 합계 대조, 스냅샷, 해시, DB 동결을 완료했다.
- [ ] 모든 4기 데이터에 서버가 검증한 `season_id`가 있다.
- [ ] 관리자 Auth 삭제가 시즌 기록을 cascade 삭제하지 않는다.
- [ ] 4기 더미데이터를 명시적으로 식별하고 제거 리허설을 완료했다.
- [ ] 실제 오픈 직전 더미데이터 제거 후 3기·4기 기준값을 재검증했다.

### 댓글과 응원 상자

- [ ] IndexedDB 댓글을 운영 DB/API로 교체했다.
- [ ] 로그인 댓글 이름을 클라이언트나 `user_metadata`가 아닌 운영자 확인 프로필에서 결정한다.
- [ ] 운영자 확인 전 로그인 댓글을 차단하고 익명 댓글과 구분한다.
- [ ] 익명 게스트 토큰 원문은 저장하지 않는다.
- [ ] 댓글 150자, 스팸, 숨김·복구·삭제, 작성자 삭제 요청을 테스트했다.
- [ ] 응원 상자의 Kakao provider, 시즌 승인, 오늘 인증, 중복 지급을 서버와 DB에서 확인한다.
- [ ] 동시 클릭, 재요청, 계정 재연결, Asia/Seoul 자정 경계를 테스트했다.

### Supabase와 배포 보안

- [ ] 모든 노출 테이블에 RLS가 켜져 있고 grants와 policies를 함께 검증했다.
- [ ] `anon`·일반 `authenticated`의 민감 테이블 직접 쓰기가 거부된다.
- [ ] service-role, Kakao 비밀값, Gemini 키가 서버 비밀 저장소에만 있다.
- [ ] Supabase Security Advisor와 RLS allow/deny 테스트를 통과했다.
- [ ] private Storage 정책, 서명 URL, 이미지 검증과 EXIF 제거를 확인했다.
- [ ] DB와 Storage를 각각 백업하고 실제 복원 시험을 완료했다.
- [ ] 보안 헤더, 오류 응답, 캐시의 사용자 간 데이터 혼합 여부를 점검했다.
- [ ] 320·360·390·412px 모바일과 주요 웹 너비, 저속 네트워크에서 첫 화면과 로그인 동선을 확인했다.

체크리스트를 모두 충족하기 전에는 4기 오픈 전 안내를 제거하지 않는다.

## 11. 현재 구현 상태와 배포 제한

2026-09-02 저장소 기준으로 카카오 OAuth 진입, Kakao provider 판정, 운영자 확인 표시명, 계정 승인 연결, 시즌 키가 있는 메시지형 응원 상자 MVP, 관리자 OTP·탭 UI, Supabase 세션 갱신 Proxy가 구현돼 있다. 개인 인증·OCR API는 4기 개인 계정에 열리지 않도록 403으로 차단했다. 3기 공개 화면과 리포트는 2026-05-05~08-12 공개 기록을 식별자 제거 후 고정한 스냅샷만 읽는다. 4기 사전 공개에서는 브라우저 전용 댓글 쓰기·답글·반응을 잠그고 더미 댓글을 읽기 전용으로 표시한다.

다음 항목은 정식 운영 전 필수 작업이다.

- TWTT Kakao 앱·Supabase provider·운영 redirect 설정과 실제 계정 검증
- 운영 Supabase에 `docs/supabase-schema.sql`과 `docs/supabase-security-hardening.sql` 적용 및 grants/RLS 검증
- 3기·4기 `seasons`, `season_participants` 도입, 운영 DB의 3기 trigger 동결과 관리자 Auth 소유권 분리
- 댓글·답글·반응의 Supabase 서버 저장, 지속형 rate limit, 운영자 숨김·복구·삭제 관리
- 응원글·배너·크루프로필의 4기 서버 저장 및 어드민 편집 API 연결
- Kakao unlink webhook과 외부 연결 해제 후 식별 정보 삭제 처리
- 실제 보관기간·삭제 처리·문의 연락처·Supabase 리전 확정
- 4기 더미데이터 제거 및 롤백·DB와 Storage 복구 시험

이 제한이 남아 있는 동안 더미데이터가 있는 4기 화면은 오픈 전 안내가 적용된 사전 공개 화면으로만 운영한다.
