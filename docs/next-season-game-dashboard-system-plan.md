# 스내사 다음 시즌 게임형 대시보드 시스템 기획서

상태: 아이디에이션·리서치 초안 0.7  
작성일: 2026-08-31  
개발 원칙: 로컬 전용. 별도 승인 전까지 GitHub 푸시, Vercel 배포, 운영 Supabase 변경을 하지 않는다.

## 1. 제품과 전환의 고정 원칙

1. 다음 시즌은 실제 게임 엔진을 먼저 도입하지 않고, 러닝 뒤 짧게 즐기는 **게임형 대시보드**로 시작한다.
2. 다음 시즌 참가자는 카카오 로그인과 시즌 참가자 연결을 거쳐 자신의 화면에 들어간다.
3. 이전 시즌의 기록과 리포트는 종료 시점 결과로 완전히 동결한다.
4. 이전 시즌 화면은 공개 서비스에서 제거하고 관리자 인증 뒤에만 읽기 전용으로 조회한다.
5. 새 시즌과 이전 시즌은 같은 저장소를 사용하더라도 라우트, 데이터 조회, 캐시, 브라우저 저장소, 디자인 토큰을 분리한다.
6. 인증·코인·순위 판정은 서버가 담당하고, 캐릭터와 빌리지 화면은 확정 결과를 표현한다.
7. 참가자가 달리는 중에는 화면 조작을 요구하지 않는다. 게임 행동은 인증 제출 뒤 1~3분 안에 끝낼 수 있게 한다.
8. 첨부 이미지는 시각 분위기 참고로만 사용한다. 특정 게임의 캐릭터, 얼굴, 건물, UI를 복제하지 않고 오리지널 동물과 자산으로 제작한다.

## 2. 안전한 전환 순서

### 0단계 — 기준선 고정

- 현재 운영 코드와 스키마를 변경하지 않고 로컬에서 회귀 기준을 기록한다.
- 이전 시즌 참가자, 기록, 뱃지, 전체 리포트, 개인 리포트의 예상 개수와 주요 합계를 보관한다.
- 기존 `package-lock.json` 사용자 변경은 다음 시즌 작업에 포함하지 않는다.

### 1단계 — 시즌과 제출 기록을 일급 데이터로 전환

- `seasons`, `season_memberships`, `season_rules`를 새로 설계한다.
- 인증 이미지 한 장마다 `run_submissions`를 만들고, 하루 합계는 `daily_certifications`로 분리한다.
- 기존 기록에는 nullable `season_id`를 먼저 추가하고 이전 시즌을 archived 상태로 연결한다.
- 백필과 합계 검증 뒤에만 시즌별 필수 제약을 강화한다.

### 2단계 — 이전 시즌 완전 동결

- 이전 시즌 전체·개인 리포트 결과를 immutable snapshot으로 생성한다.
- 동결 뒤 원본 기록을 수정해도 스냅샷이 자동 재계산되지 않게 한다.
- 관리자 화면은 원본과 스냅샷을 읽기 전용으로 조회한다.
- 법적 삭제가 필요한 경우에만 별도 비식별화 절차를 사용하고 일반 수정 기능은 열지 않는다.

### 3단계 — 카카오 로그인과 참가자 연결

- Kakao Authorization Code + PKCE(S256) + OIDC를 서버 경유 방식으로 구현한다.
- 카카오 계정과 시즌 참가 자격을 분리하며 이메일이나 이름만으로 자동 연결하지 않는다.
- 미승인, 탈퇴, 시즌 미참가 사용자는 게임 데이터와 개인 인증에 접근하지 못한다.
- 개발 중에는 로컬 callback과 mock identity를 사용하고 운영 자격증명은 저장소에 넣지 않는다.

### 4단계 — 인증·관리자·코인 원장

- 참가자 직접 이미지 제출과 운영자 대리 이미지 등록을 같은 제출 모델로 통합한다.
- 여러 기록을 하루 단위로 합산하고 승인된 거리만 코인과 순위에 반영한다.
- 코인 잔액을 직접 덮어쓰지 않고 append-only 원장을 구축한다.
- 기록 정정은 원본 삭제 대신 반전·조정 이벤트로 처리한다.

### 5단계 — 새 시즌 경량 셸

- 서버 렌더링으로 시즌 일자, 오늘의 인증 상태, 코인, 빌리지 진행률을 먼저 표시한다.
- 공개 화면에는 공개용 compact snapshot만 전달한다.
- 캐릭터와 지도 자산은 화면 진입 뒤 지연 로딩한다.
- 게임 모듈이 실패해도 인증과 텍스트 순위를 사용할 수 있는 lite 화면을 제공한다.

### 6단계 — 게임형 경험

- 캐릭터 선택과 꾸미기, 이동, 개인 집, 공동 부지, 응원 선물을 순서대로 연다.
- 첫 주에는 인증, 코인, 이동, 기본 집만 노출하고 상점과 공동 건설은 단계적으로 안내한다.
- 실시간 멀티플레이, 충돌 판정, 자유 채팅, 거래소, 확률형 아이템은 MVP에서 제외한다.

### 7단계 — 로컬 전환 검증

- 이전 시즌 불변성, 계정 격리, 관리자 권한, 다중 기록 합산, 코인 멱등성을 테스트한다.
- 360px 모바일, 저사양 모드, 느린 네트워크, reduced motion, 키보드 접근을 확인한다.
- 공개 API에 인증 사진, 카카오 식별자, 이전 시즌 비공개 데이터가 포함되지 않는지 검사한다.

## 3. 제품 콘셉트 0.7 — 함께 꾸미는 포근한 스내사빌리지

### 핵심 루프

```text
러닝 완료
→ 참가자 또는 운영자가 인증 이미지 제출
→ OCR·필수값·중복·파일 안전성 자동 검증
→ 유효 기록 자동 반영 및 해당 날짜 거리 합산
→ 거리·연속일·코인 갱신
→ 캐릭터의 짧은 성장 반응
→ 이동·의상·집·공동 꾸미기 중 소비처 선택
→ 빌리지 변화와 독립 순위 반영
```

큰 구매를 할 수 없는 날에도 캐릭터 표정, 발자국 도감, 집 앞 꽃, 계절 수집 기록처럼 코인을 소모하지 않는 작은 변화가 있어야 한다. 고가 상점만 존재하면 평균 참가자는 대부분의 날에 게임 피드백을 받지 못한다.

### 하루 경험

1. 홈에서 Day N/100, 오늘 인증 상태, 현재 코인, 보호 스트릭을 확인한다.
2. 참가자가 이미지를 올리거나 운영자가 대신 이미지를 등록한다.
3. OCR 결과에서 필수인 날짜·거리와 선택인 시간·앱명을 확인한다.
4. 필수값·파일 안전성·중복 검사를 통과하면 자동 반영한다. 이상 거리는 막지 않고 관리자에게만 표식한다.
5. 같은 날짜의 모든 유효 기록을 합산하고 그날 목표 코인과 이미 지급한 코인의 차액만 반영한다.
6. 캐릭터가 3~5초 동안 기뻐하고 당일 변화나 도감 조각을 보여준다.
7. 참가자는 코인을 이동, 휴식권, 의상, 집, 공동 꾸미기, 응원 중 원하는 곳에 사용한다.
8. 마지막 위치와 배치 상태를 저장하고 다음 방문 때 그대로 이어간다.

### 경험치·레벨 제안 — 미확정

코인은 거리 기반 선택 재화로 두고, 경험치는 꾸준함을 보여주는 성장 축으로 분리한다.

```text
하루 경험치 = 승인 인증 기본 10XP + floor(그날 승인 거리 km)
휴식권 사용일 = 0XP
```

- 거리는 코인처럼 상한 없이 경험치에 반영하되, 기본 10XP로 짧은 러닝도 성장하게 한다.
- MVP 레벨은 1~20, 레벨당 100XP를 제안한다.
- 레벨은 코인 생산 배율이나 순위 보너스를 주지 않고 표정, 대기 동작, 명패, 도감 페이지를 연다.
- 거리와 스트릭 이정표 보상은 판매 아이템과 겹치지 않는 비거래 장식으로 둔다.

| 조건 | 무료 성장 보상 예시 |
| --- | --- |
| 실제 연속 인증 3일 | 첫 기쁨 표정 |
| 7일 | 러닝 준비 대기 동작 |
| 14일 | 집 명패 테두리 |
| 30일 | 계절 포즈 |
| 50일 | 특별 발자국 |
| 75일 | 캐릭터 오라 |
| 100일 | 100일 완주 명예 의상·동상 |
| 누적 25km | 잎사귀 발자국 |
| 50km | 숲길 표지판 |
| 100km | 반짝이는 이동 흔적 |
| 200km | 집 앞 러닝 깃발 |
| 300km | 마을 기념 표식 |
| 500km | 시즌 거리 기념 연출 |

승인된 날마다 코인과 별개인 잎사귀 도장 1개를 100일 도감에 찍어, 구매가 없는 날에도 눈에 보이는 수집 진행을 제공한다. 이 무료 잎사귀 도감은 확정 기능이다.

## 4. 러닝 인증과 운영자 대리 등록

### 두 개의 입력 경로

#### 참가자 직접 제출

1. 카카오 로그인과 시즌 연결을 완료한다.
2. 러닝 활동 발생일과 업로드일이 모두 당일 00:00:00~23:59:59 KST 안인 이미지 한 장 이상을 올린다.
3. OCR 결과의 날짜와 거리는 필수로 확인하고, 시간과 앱명은 값이 있을 때만 확인한다.
4. 필수값·파일 안전성·중복 검사를 통과하면 자동으로 `APPROVED`가 되어 거리와 코인에 반영된다.
5. 이례적인 거리라는 이유만으로 보류하거나 상한을 적용하지 않고 관리자 화면에 비차단 표식만 남긴다.

#### 운영자 대리 제출

1. 운영자가 참가자와 활동일을 선택한다.
2. 인증 이미지를 한 장 이상 업로드한다.
3. OCR 결과를 수정하거나 거리·시간·출처 앱을 직접 입력한다.
4. 활동 날짜와 거리는 필수이며 시간과 출처 앱은 선택이다.
5. 운영자는 참가자 마감 뒤에도 과거 활동일 기록을 추가·정정할 수 있고 별도 사유는 요구하지 않는다.
6. 참가자 제출과 동일한 일일 합계에 즉시 포함한다.
7. 참가자 화면에는 `운영자 대리 등록` 출처와 처리 시각을 표시하고, 시스템은 작업자·처리 시각·변경 전후 값을 자동 감사 기록한다.

| 상태 | 의미 | 거리·코인·순위 반영 |
| --- | --- | --- |

### 하루 합산과 코인 계산

코인은 이미지마다 버림하지 않고 참가자·시즌·KST 활동일별 승인 거리를 모두 합친 뒤 한 번 계산한다. 원본 거리는 소수점 km까지 보존하고, **그날 합계의 100m 미만만 코인 발행에서 버린다.** 버린 거리는 다음 날로 이월하지 않는다.

```text
일일 코인 = floor(해당 날짜의 승인 거리 합계 m / 100)
추가 지급 = 새 일일 코인 - 이미 지급된 일일 코인
```

예: 2.55km가 먼저 반영되면 25코인, 이후 3.48km가 추가되면 합계 6.03km이므로 35코인을 추가 지급한다. 원장에는 그날 60코인이 발행되지만 기록에는 6.03km가 그대로 남는다.

### 현재 시스템에서 확인된 변경점

- 현재 어드민에는 이미지 드래그앤드롭, OCR, 직접 입력 기능이 이미 있다.
- 현재 `daily_run_records`는 `UNIQUE(user_id, participant_id, record_date)`이고 저장 API가 날짜 기준 upsert이므로 하루 여러 기록을 보존할 수 없다.
- 다음 시즌에는 기존 테이블을 억지로 확장하기보다 이미지 단위 `run_submissions`와 날짜 단위 `daily_certifications`를 분리한다.
- 기존 이전 시즌 테이블과 API는 동결 호환용으로 유지하고 새 시즌 쓰기 경로에서 사용하지 않는다.

## 5. 100m당 1코인 경제

### 100일 획득량과 가격 체감

| 하루 평균 거리 | 하루 코인 | 1인 100일 총 코인 | 20명 100일 총공급 |
| ---: | ---: | ---: | --- |
| 3km | 30 | 3,000 | 60,000 |
| 5km | 50 | 5,000 | 100,000 |
| 10km | 100 | 10,000 | 200,000 |

100일 모두 인증한다는 단순 상한 비교이며 휴식·누락일만큼 실제 공급은 줄어든다. 일일·시즌 획득 상한은 두지 않는다. 이례적인 거리도 자동 반영하고 관리자 화면에 비차단 표식만 남긴다. 다만 정확히 같은 파일의 재전송처럼 명백한 기술적 중복은 이중 지급을 막아야 한다. 공개 화면에는 산식, 반영 상태, 갱신 시점을 명확히 표시한다.

### 현재 가격을 그대로 둘 때의 실제 난이도

| 항목 | 현재 가격 | 필요한 누적 거리 | 3km/일 기준 | 10km/일 기준 |
| --- | ---: | ---: | ---: | ---: |
| 이동 1칸 | 10 | 1km | 약 0.3일 | 하루 10칸 가능 |
| 휴식권 | 100 | 10km | 약 3.3일 | 1일 |
| 마을 아이템 | 200~5,000 | 20~500km | 약 6.7~166.7일 | 2~50일 |
| 일반 의상 | 300 | 30km | 10일 | 3일 |
| 특수 의상 | 2,000 | 200km | 약 66.7일 | 20일 |
| 집 테마 | 3,000 | 300km | 100일 | 30일 |
| 캐릭터 변경 | 5,000 | 500km | 약 166.7일 | 50일 |
| 응원 선물 | 1,000 | 100km | 약 33.3일 | 10일 |

`100m = 1코인`에서는 이동이 매일 가능한 행동이 되고, 일반 의상은 단기 목표, 휴식권·응원은 중기 목표, 특수 의상·집 테마·캐릭터 변경은 장기 목표가 된다. 3~10km/일 참가자 모두 시즌 중 의미 있는 선택지가 생기므로 현재 가격표와 게임 루프를 함께 유지할 수 있다.

### 코인 원장

| 이벤트 | 의미 |
| --- | --- |
| `RUN_EARN` | 승인 거리로 획득 |
| `REST_PASS_BUY` | 휴식권 구매 |
| `MOVE` | 지도 이동 |
| `ITEM_BUY` | 의상·테마·재료 구매 |
| `VILLAGE_PLACE` | 공동 영역 실제 배치·재료 소비 |
| `CHEER_CREATE` | 직접 획득 코인으로 새 응원 생성 |
| `CHEER_FORWARD` | 받은 응원 코인 재전달 |
| `ADMIN_ADJUST` | 운영자 정정 |
| `REFUND` | 허용된 환불 |
| `REVERSAL` | 이전 거래 반전 |

- 잔액을 직접 수정하지 않고 모든 변화에 거래 ID, 원천 제출, 적용일, 처리 시각을 남긴다. 사유는 정정·환불처럼 필요한 사건에만 두며 관리자 소급 입력에는 요구하지 않는다.
- 같은 요청이 재전송돼도 한 번만 처리되도록 멱등 키와 DB 고유 제약을 사용한다.
- 정정으로 잔액이 음수가 되면 이미 배치한 건물을 철거하지 않고 이후 획득 코인에서 상계한다.
- 공개 또는 본인 화면에는 총 획득, 현재 잔액, 받은 선물, 보낸 선물, 개인 소비, 공동 소비를 분리한다.

### 휴식권

확정된 부분:

- 1개 100코인
- 최대 10개 보유
- 연속 사용 가능
- 코인 구매만 가능하고 10일 인증 같은 별도 구매 자격은 없음
- 참가자가 직접 적용하는 수동 사용만 가능

권장 기본 동작:

- 휴식일에는 거리, 코인, 인증 횟수, 성장 보상을 지급하지 않고 보호 스트릭만 유지한다.
- 달력에서는 실제 인증일과 휴식권 사용일을 다른 아이콘으로 표시한다.
- 공개 표기는 `연속 참여 24일 · 실제 인증 21일 · 휴식 3일`처럼 분리한다.
- 공개 순위는 휴식권을 제외한 실제 연속 인증만 사용한다.
- 자동 사용은 제공하지 않으며 구매·적용 전 대상 날짜와 효과를 미리 보여준다.

### 1,000코인 응원과 재선물

확정된 A 구조는 `1,000코인이 상대에게 실제 전달되고 응원 스티커가 함께 붙는 한 번의 행동`이다. `직접 번 코인만 새 선물 생성 가능`과 `받은 선물 재전달 가능`을 동시에 지키려면 출처를 분리한다.

- 새 응원 생성: `earned_coin` 1,000개를 사용한다.
- 이어 보내기: 수신한 1,000코인 선물 묶음을 다른 참가자에게 전달한다.
- 재선물해도 최초 생성 거래와 모든 전달 경로가 연결된다.
- 선물 이동은 코인을 새로 만들지 않으며 선물 횟수는 공개 순위에 포함하지 않는다.
- 선물을 보낸 실제 전달자의 생산 기여도에 전달액 1,000을 더한다.
- 발신·수신 총횟수는 제한하지 않되 API 폭주 방지 속도 제한, 수신 거부, 사용자 차단, 신고는 둔다.
- 받은 묶음을 다시 전달할 때도 동일한 묶음 ID와 최초 생성·모든 전달 경로를 보존한다.

### 생산 기여도

사용자가 확정한 기준을 시스템 산식으로 풀면 다음과 같다.

```text
생산 기여도
= 공동 영역에 실제 배치된 아이템의 결제액
+ 공동 건설에 실제 소비된 재료의 결제액
+ 응원 선물을 실제 전달한 금액
- 환불된 금액
```

- 구매만 하고 보관한 아이템은 반영하지 않는다.
- 같은 아이템의 위치를 옮겨도 다시 반영하지 않는다.
- 개인 마당, 집 테마, 의상, 이동, 휴식권, 캐릭터 변경은 제외한다.
- 응원 묶음을 재전달할 때마다 실제 전달자에게 1,000 기여를 더하는 문언 그대로의 규칙은 같은 묶음을 왕복해 순위를 무제한 올릴 수 있으므로, 반복 전달 기여 인정 방식은 구현 전에 한 번 더 확정한다.
- 사용자에게는 `생산 기여도`보다 `빌리지 꾸미기 기여도`가 산식을 더 정확히 설명할 수 있다.

### 꾸미기 슬롯 제안

MVP는 제작량과 모바일 가독성을 고려해 다음 네 슬롯을 권장한다.

1. 몸 의상
2. 머리 장식
3. 얼굴·표정
4. 손 소품

발자국·잎사귀·별가루 같은 이동 연출은 별도 슬롯으로 두되 저사양·reduced motion에서는 끈다.

### 경량 구현

- 실시간 3D와 WebGL 대신 미리 렌더링한 WebP/AVIF 캐릭터와 2.5D 타일을 사용한다.
- 캐릭터는 4방향, idle 2프레임, walk 2프레임부터 시작한다.
- 의상은 공통 몸체에 맞춘 레이어 자산으로 합성한다.
- 지도는 DOM/SVG 좌표와 CSS transform으로 움직인다.
- 현재 화면 근처 타일만 로드하고 화면 밖 캐릭터는 정적 마커로 축약한다.
- 캐릭터·집·공동 아이템 atlas를 기능 진입 시 지연 로딩한다.

## 8. 계정·관리자·업로드 보안

### 카카오 로그인 권장 구조

```text
브라우저
→ 우리 서버
→ Kakao Authorization Code + PKCE(S256) + OIDC
→ ID 토큰 검증
→ 우리 서버 세션 발급
```

- 로그인마다 `state`, `nonce`, `code_verifier`를 새로 만들고 짧은 시간 안에 한 번만 사용한다.
- 콜백에서 ID 토큰의 서명, `iss`, `aud`, `exp`, `nonce`를 검증한다.
- redirect URI는 정확히 등록된 HTTPS 주소만 허용한다.
- 카카오 client secret과 Admin Key는 서버에만 두고 브라우저·로그·저장소에 노출하지 않는다.
- 브라우저에는 카카오 토큰을 보관하지 않고 `Secure`, `HttpOnly`, `SameSite=Lax` 자체 세션 쿠키를 사용한다.
- 카카오 API를 지속 호출하지 않는다면 로그인 확인 뒤 액세스·리프레시 토큰을 장기 보관하지 않는다.
- 카카오 사용자 고유 식별에는 이름이 아니라 OIDC `sub`를 반드시 사용한다. 이름은 중복·변경될 수 있어 로그인 키나 과거 기록 연결 키가 될 수 없다.
- 이메일, 전화번호, 카카오 사진은 받지 않는다.
- 표시 이름만 필요하면 가장 작은 동의 범위는 `openid`이고, 로그인 뒤 서비스에서 시즌 이름을 확인받는 방식이다.
- 카카오 프로필 닉네임을 초기값으로 쓰려면 `openid,profile_nickname`을 요청한다. 이는 사용자가 바꿀 수 있는 닉네임이지 실명 인증이 아니다.
- 카카오계정의 일반 이름을 받으려면 운영 앱에서 `name` 동의항목 권한을 승인받고 `openid,name`으로 동의받은 뒤 `/v2/user/me`를 호출해야 한다. 이 값도 법적 본인확인 결과가 아니며 미제공 fallback이 필요하다.
- 로그인 확인 뒤 카카오 API를 더 쓰지 않으면 액세스·리프레시 토큰은 폐기한다.

근거: [카카오 OIDC Discovery](https://kauth.kakao.com/.well-known/openid-configuration), [카카오 로그인 보안 권장 사항](https://developers.kakao.com/docs/ko/getting-started/security-guideline), [사용자 정보와 동의항목](https://developers.kakao.com/docs/ko/kakaologin/utilize), [REST 사용자 정보](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [개인정보 동의항목 설정](https://developers.kakao.com/docs/ko/kakaologin/prerequisite)

### 계정 연결

- `identities`에는 `(kakao_app_id, sub)`를 저장한다.
- `accounts`와 `season_memberships`를 분리한다.
- 한 카카오 식별자는 동시에 두 서비스 계정에 연결할 수 없다.
- 한 시즌 참가자 자리는 한 서비스 계정에만 연결한다.
- 같은 이메일이나 같은 시즌 이름만으로 기존 기록을 연결하지 않는다.
- 운영자 발급 1회용 초대 코드 또는 사전 명단 승인을 권장한다.
- 계정 분실·변경은 재인증, 운영자 승인, 변경 이력 기록을 거친다.

### 관리자 1명 운영

- 공유 관리자 계정을 사용하지 않는다.
- 관리자 여부와 대상 권한을 모든 요청에서 서버가 확인한다.
- 관리자 로그인은 계정 allowlist와 Passkey 또는 TOTP MFA를 조합한다.
- 관리자 1명이므로 작성자·승인자 분리는 적용하지 않는다. 대리 등록은 즉시 반영하되 MFA, 변경 전후값, 작업자, 처리 시각을 자동 기록한다.
- 마감 뒤 기록 추가에도 사유 입력을 요구하지 않는다.
- 계정 복구 코드, 로그인 기기·세션 목록, 전체 기기 로그아웃, 민감 작업 전 재인증을 제공한다.
- 민감 작업은 `create/approve/reject/correct/reverse/freeze/unfreeze` 이벤트로 append-only 감사로그에 남긴다.

근거: [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html), [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

### 이미지 보안

- MVP 허용 형식은 JPEG와 PNG로 제한한다.
- 아이폰 HEIC는 안전한 서버 디코더와 재인코딩이 준비된 뒤 추가한다.
- 확장자와 브라우저 MIME만 믿지 않고 magic bytes와 실제 디코딩을 확인한다.
- 원본 10MB, 최대 4096px 또는 12MP를 제안한다.
- 디코딩 뒤 WebP/JPEG로 재인코딩해 EXIF GPS, 기기명, 활성 콘텐츠를 제거한다.
- UUID 객체 키를 쓰고 private storage에 저장한다.
- 본인과 권한 있는 관리자에게만 짧은 TTL의 signed URL을 발급한다.
- 동일 참가자·활동일·파일 SHA-256은 중복으로 막고, 다른 참가자나 날짜의 동일 파일은 검수 큐로 보낸다.
- 인증 사진은 본인과 관리자만 볼 수 있고, 시즌 종료 30일 뒤 원본·썸네일·백업을 같은 정책으로 삭제한다. 삭제 뒤에는 날짜·거리·입력 출처·해시 같은 비이미지 증빙만 보존한다.

근거: [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

## 12. 4차 답변 반영 결과

- 예상 규모는 참가자 20명, 관리자 1명이며 참가자 하루 거리는 3~10km다.
- 러닝 활동 발생일과 참가자 인증 제출일 모두 KST 00:00:00~23:59:59를 적용한다.
- 운영자는 마감 뒤에도 과거 기록을 넣을 수 있고 사유는 요구하지 않는다.
- 날짜·거리는 필수, 시간·앱명은 선택이다.
- 일일 합산 뒤 100m 미만은 코인으로 이월하지 않지만 원거리 기록은 보존한다.
- 이례적인 기록은 상한이나 수동 승인 없이 자동 반영한다.
- 휴식권은 100코인 구매와 수동 사용만 허용하고, 최대 10개·연속 사용 규칙을 유지한다.
- 공개 연속 순위는 휴식권을 제외한 실제 연속 인증을 사용한다.
- 응원은 1,000코인 묶음이 상대에게 전달되고 스티커가 함께 가는 A 구조다.
- 선물 묶음의 최초 출처와 모든 재전달 경로를 추적한다.
- 선물을 실제 전달한 참가자의 생산 기여도가 올라간다.
- 1회용 초대, 최소 카카오 동의, 토큰 폐기, 관리자 MFA, 비공개 사진, 시즌 종료 30일 뒤 사진 삭제를 적용한다.
- 무료 잎사귀 도감을 제공한다.
- 최종 코인 환율은 **100m당 1코인**이다.

## 13. 아이디에이션 질문 — 5차

### A. 경제와 선물 — 구현 전 최우선

1. 같은 1,000코인 선물 묶음이 A→B→A→B로 왕복할 때마다 각 전달자의 생산 기여도에 1,000을 계속 더하는 것이 의도인가? 무한 반복을 막는 권장안은 `(선물 묶음, 전달자)` 조합당 기여를 한 번만 인정하는 것이다.
2. 자기 자신에게 선물은 금지하고, 자유 메시지는 60자와 신고·숨김·수신 거부를 함께 제공할 것인가?
3. 지표 이름은 `생산 기여도`를 유지할 것인가, 산식이 잘 드러나는 `빌리지 기여도`로 바꿀 것인가?

### B. 카카오 이름과 계정 복구

4. 말한 `이름`은 시즌 공개 이름, 카카오 프로필 닉네임, 카카오계정 일반 이름 중 어느 것인가? 최소 수집 권장안은 `openid`로 계정만 식별하고 시즌 공개 이름을 참가자가 확인하는 방식이다.
5. 카카오계정 일반 이름을 꼭 받아야 한다면 `name` 권한 심사와 값 미제공 시 직접 입력 fallback을 수용할 것인가?

### C. 인증·동결·휴식권

7. 이례적인 거리는 자동 반영하되, 동일 파일 해시 재업로드와 필수값 누락은 이중 지급·오입력을 막기 위해 차단하는 것으로 확정할 것인가?

11. 관리자 소급 인증이 들어오면 해당 날짜의 잎사귀와 실제 스트릭도 과거부터 다시 계산할 것인가?

### D. 캐릭터·지도·운영 UX

12. 동물 20종은 중복 선택을 허용할 것인가? 20명이 한 종씩 독점하면 가입 순서가 캐릭터 선택권을 결정한다.
