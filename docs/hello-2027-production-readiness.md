# Hello 2027 배포·데이터 보존·어드민 운영 가이드

기준일: 2026-09-06

## 먼저 알아야 할 현재 상태

기존 `/poc/hello-2027`과 `/poc/hello-2027/manage` 개발 화면 및 IndexedDB 어댑터는 제거했다. 해당 PoC 데이터는 운영 원본이나 이관 원본으로 사용하지 않는다.

배포된 `/4th/dashboard`는 공개 콘텐츠 서버 API와 관리자 Supabase CRUD를 사용한다. 별도의 대시보드 전환 플래그 없이 4기 공식 기록으로 당일·주간·월간 인증률을 계산하며, 운영 환경변수·관리자·시즌 컬럼·테이블·4기 멤버가 없거나 조회가 실패하면 코드 fixture를 섞지 않는 빈 4기 상태로 실패-폐쇄한다. 댓글은 기본 활성이고 카카오 로그인 이용자만 닉네임 또는 공개 익명으로 쓸 수 있다. DB·권한 조회 실패 시 입력을 잠그며 `HELLO_2027_COMMENTS_DISABLED=true`로 긴급 중단할 수 있다. 4기 정식 오픈 안내 제거는 아직 운영 승인 대상이다.

## 현재 기존 데이터를 보는 경로

| 목적 | 현재 경로 | 주의점 |
| --- | --- | --- |
| 4기 참가자·러닝 기록 관리 | `/admin` | 관리자 이메일 OTP와 2시간 서명 쿠키 사용. API는 `season_key = '4th'`만 조회·변경 |
| 현재 공개 대시보드 진입 | `/dashboard` | 현재 시즌 `/4th/dashboard`로 이동 |
| TWTT 3기 공통 화면 | `/3th` | 2026-05-05~2026-08-12 식별자 제거 정적 스냅샷 |
| TWTT 3기 전체 리포트 | `/dashboard/report/3th` | 같은 3기 동결 공개본을 읽는 전체·개인 리포트 |
| TWTT 3기 개인 리포트 | `/dashboard/report/3th/[participantId]` | 공개 전용 식별자를 사용한 읽기 전용 화면 |
| 카카오 개인 영역 | `/4th/dashboard` 또는 `/me` | 운세와 조건부 응원 상자만 제공하며 개인 인증·OCR 쓰기는 `403` |

공개 3기 화면은 코드의 동결 스냅샷을 읽어 운영 테이블 수정과 분리돼 있다. Supabase 원본에는 먼저 `season_key = '3th'` 백필과 합계 대조를 적용해야 하며, DB trigger 동결과 Storage 백업은 별도로 완료해야 한다.

## 권장 최종 메뉴

기존 `/admin`의 OTP 흐름과 참가자·기록·OCR 기능을 확장해 상단에 시즌 선택기를 둔다.

- `TWTT 4기 · Hello 2027 — 진행 중`
- `TWTT 3기 · 100일 — 동결`

Hello 2027 시즌에는 다음 탭을 제공한다.

| 탭 | 운영 기능 |
| --- | --- |
| 크루 | 시즌 참가자 등록·수정·제외, 표시 순서, 캐릭터, 얼굴, 소개 제목·자기소개 및 동의 상태 |
| 인증 | 날짜·크루별 조회, 직접 입력, OCR 일괄 등록, 승인·반려·수정, 일일 합산 재계산 |
| 광고 | 최대 10개, 이미지·문구·대체 텍스트·초점 위치, 순서, 게시/중지, 웹·모바일 미리보기 |
| 응원글 | 최대 56개, 등록·수정·순서, 활성/비활성 |
| 댓글 | 공개/숨김/삭제 필터, 답글·반응 수, 숨김·복구·비식별 삭제 |
| 응원 상자 | 문구, 톤, 가중치, 게시 기간, 개봉 이력·통계 관리 |
| 이전 시즌 | 전체·개인 최종 리포트, CSV/JSON 내려받기, 읽기 전용 |
| 변경 이력 | 운영자가 바꾼 대상, 변경 전·후 값, 시각 조회 |

기존 `/admin`의 참가자 CRUD, 직접 기록 입력, OCR 일괄 등록에 응원글·배너·댓글·크루 자기소개·카카오 계정 연결 관리가 추가됐다. 정식 시즌 선택, 3기 DB 동결, 변경 감사 로그와 응원 상자 운영 통계는 후속 운영 기능이다.

## 최소 서버 데이터 구조

기존 Supabase 테이블을 버리지 않고 다음 구조를 추가하는 방식이 가장 안전하다.

### 시즌과 권한

- `app_admins`: 관리자 auth user, `owner | operator` 역할, 활성 상태
- `seasons`: 이름, 기간, 타임존, 마감 시각, 최소 거리, `draft | active | archived`, `frozen_at`
- `season_participants`: 시즌별 참가자, 당시 표시명, 순서, 캐릭터, 얼굴, 소개 제목·자기소개, 동의 상태

현재 `participants.active`는 모든 시즌에 공통으로 영향을 주므로, 시즌 참가 상태를 `season_participants`로 분리해야 과거 리포트가 보존된다.

### 인증

- 기존 `daily_run_records`에 `season_id`, 합산 거리, 마감 전 거리, 인증 완료 여부, 확정 시각 추가
- `run_activity_entries`: 하루 여러 활동, 원본 증빙, OCR 결과, 승인 상태, 관리자 메모

한 날짜에 여러 활동이 있으면 `run_activity_entries`를 원본으로 보관하고 승인된 활동을 `daily_run_records`에 합산한다. 수동 수정 시 해당 날짜 집계를 같은 트랜잭션에서 다시 계산한다.

### 콘텐츠와 댓글

- `dashboard_ads`: 시즌, 소유 크루, 이미지 경로, 제목, 설명, 대체 텍스트, 모바일 초점, 순서, 게시 상태
- `encouragements`: 시즌, 본문, 순서, 활성 상태
- `guestbook_comments`: 시즌, 부모 댓글, 작성자 표시 방식, 표시명, 본문, 공개 상태, 게스트 토큰 해시
- `guestbook_reactions`: 댓글, 이모지, 게스트 토큰 해시; `(comment_id, guest_token_hash, emoji)` 고유

광고 10개, 응원글 56개, 댓글 150자 제한은 클라이언트뿐 아니라 API와 DB 제약에서도 다시 검사한다.

### 오늘의 응원 상자

- `gift_box_prizes`: 시즌별 응원 문구, 톤, 가중치, 활성 기간
- `daily_gift_claims`: 시즌 참가자·인증일별 1회 개봉 결과와 당시 문구 스냅샷

상자는 자동 연결된 로그인 참가자가 2026-08-13~12-31 사이의 당일 인증을 완료했는지 서버에서 확인한 뒤 지급한다. 9월 23일 전 준비 러닝은 상자 자격과 개인 기록에는 쓰지만 공식 인증률에는 포함하지 않는다. 공개 멤버 카드나 브라우저 IndexedDB만으로 지급하지 않는다. 상세 흐름과 API·보안 기준은 [TWTT 4기 오늘의 응원 상자 기획](./hello-2027-daily-gift-box-plan.md)을 따른다.

### 보존과 감사

- `season_snapshots`: 최종 JSON, 레코드 수, SHA-256, 생성자·생성 시각
- `admin_audit_logs`: 운영자, 동작, 대상, 변경 전·후 값, 요청 ID

동결된 시즌의 snapshot과 audit log는 append-only로 두고 일반 update/delete를 허용하지 않는다.

## 이전 시즌 안전 전환 순서

1. Supabase DB 백업과 private Storage의 `photos`, `snasa-gallery` 객체 목록·파일 백업을 만든다.
2. 현재 참가자 수, 기록 수, 날짜별 인증 수, 거리·시간 합계를 기준값으로 저장하고 기존 행이 모두 3기인지 확인한다.
3. 이미 수동 입력한 4기 행이 있다면 SQL 실행 전에 `season_key = '4th'`를 명시한다.
4. `docs/supabase-schema.sql`을 적용해 기존 NULL 시즌을 `3th`로 백필하고 신규 참가자·배치·인증·뱃지·계정 연결의 기본 시즌을 `4th`로 잠근다.
5. 백필 전후 참가자·기록·거리·시간 합계를 대조하고 4기 관리자 API가 3기 행을 반환하지 않는지 확인한다.
6. 현재 3기 전체·개인 리포트를 `season_snapshots`에 저장하고 해시를 기록한다.
7. 3기를 `archived`로 전환하고 DB trigger와 API 양쪽에서 수정·삭제를 차단한다.
8. 기존 공개 리포트는 관리자 전용 `/admin/seasons/[seasonId]/report`로 옮기거나 별도 공개 정책을 확정한다.
9. 광고·응원글·크루 자기소개는 운영자가 검토해 Supabase에 등록한 실제 콘텐츠만 사용하고 코드 fixture나 이전 PoC 데이터를 seed로 복사하지 않는다.
10. 제거된 PoC IndexedDB의 브라우저 로컬 데이터는 운영 데이터로 자동 이관하지 않는다.

최신 스키마는 운영 데이터의 관리자 `user_id` FK를 `ON DELETE RESTRICT`로 바꿔 관리자 Auth 계정의 실수 삭제가 참가자·인증·콘텐츠 연쇄 삭제로 이어지지 않게 한다. 다만 운영 소유권을 장기적으로 `seasons`/`app_admins` 같은 별도 엔터티로 이관하기 전에는, 담당자 교체 시 기존 계정을 먼저 지우지 말고 새 운영자 권한과 데이터 소유권을 검증해 이관한다.

## 보안 필수 조건

- `ADMIN_SESSION_SECRET`을 필수 환경변수로 만들고 service-role key fallback을 제거한다.
- `DAILY_FORTUNE_SECRET`을 32바이트 이상의 당일 캐시 서명 전용 비밀값으로 두고 다른 키와 재사용하지 않는다.
- `daily_fortune_usage`와 원자적 호출 제한 함수를 적용하고, 가능하면 OCR과 다른 `GEMINI_FORTUNE_API_KEY`를 사용한다.
- Supabase 연결을 의도적으로 끊는 장애 리허설에서도 코드 fixture가 나타나지 않고 빈 4기 상태로 실패-폐쇄하는지 확인한다.
- 소스의 하드코딩 관리자 이메일 대신 `app_admins`에서 최종 권한을 확인한다.
- 가능하면 OTP에 TOTP 또는 Passkey MFA를 추가한다.
- service-role key는 서버에서만 사용하고 브라우저 번들에는 절대 포함하지 않는다.
- Supabase anon/publishable key는 공개 클라이언트 키이므로 숨김을 보안 대책으로 삼지 않고 RLS와 grants를 검증한다.
- 익명 사용자가 Supabase에 직접 insert하지 못하게 하고 댓글·반응은 Next API만 통과시킨다.
- 댓글·반응 API에 동일 출처 검사, 지속형 rate limit, 스팸 방지, 150자 서버 검증을 적용한다.
- 카카오 반응 행의 `auth_user_id`가 저장되고, `actor_key LIKE 'user:%' AND auth_user_id IS NULL`인 레거시 반응이 0건인지 확인한 뒤 댓글 쓰기를 연다.
- 업로드는 MIME 문자열만 믿지 않고 magic bytes 확인, 실제 디코딩, 재인코딩, EXIF 제거를 서버에서 수행한다.
- 얼굴·광고·인증 증빙은 용도별 private bucket에 저장하고 공개 화면에는 허용한 변환본만 제공한다.
- 동결 시즌은 service role도 우회하지 못하도록 PostgreSQL trigger에서 쓰기를 막는다.
- 공개 DTO에서는 증빙 원본, 정확한 활동 시각, OCR 원문, 관리자 메모를 제외한다.

로그인 없이 쓰는 “실명”은 인증된 이름이 아니라 사용자가 입력한 표시명이다. 화면과 운영 정책에서 실제 신원 인증으로 오해하게 표시하면 안 된다.

## 정식 오픈 승인 게이트

다음 항목이 모두 끝나기 전에는 `/4th/dashboard`의 오픈 전 팝업·`noindex`·댓글/응원 상자 실패-폐쇄 플래그를 해제하지 않는다.

- 이전 시즌 백업·백필·합계 대조·snapshot·동결 완료
- 4기 실데이터와 Supabase 장애 시 빈 상태를 모두 확인하고, 코드 fixture가 반환되지 않는지 검증
- 공개 Hello 2027 서버 조회 API 연결
- 관리자 인증과 `app_admins` 역할 확인 연결
- 크루·인증·광고·응원글·댓글 관리 탭 연결
- 응원 상자 지급·중복 방지·관리 기능 연결
- 댓글·반응·업로드의 서버 검증과 지속형 rate limit 적용
- production 환경변수와 private Storage 정책 검증
- 웹·모바일 접근성, 성능, 오류 상태, 빈 데이터 상태 검증
- 롤백 절차와 DB/Storage 백업 복원 테스트 완료

현재 코드는 서버 실제 데이터 또는 빈 상태만 사용하도록 정리돼 있다. 다음 운영 단계는 검토된 SQL 적용, Kakao 실계정·RLS·삭제·백업 복구 검증, 지속형 남용 방지 적용, 장애 시 빈 상태 재검증 순서다.
