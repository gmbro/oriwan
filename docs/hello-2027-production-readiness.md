# Hello 2027 배포·데이터 보존·어드민 운영 가이드

기준일: 2026-09-02

## 먼저 알아야 할 현재 상태

`/poc/hello-2027`과 `/poc/hello-2027/manage`는 현재 **개발 환경 전용**이다. 두 페이지 모두 production에서는 `notFound()`를 반환한다. 또한 PoC에서 추가한 광고·얼굴·자기소개·응원글·댓글·반응은 Supabase가 아니라 해당 브라우저의 IndexedDB(`twtt-hello-2027-poc`)에 저장된다.

따라서 지금 개발 가드만 제거해서 배포하면 다음 문제가 생긴다.

- 공개 페이지와 관리 페이지의 데이터가 기기·브라우저 사이에서 공유되지 않는다.
- 브라우저 데이터 삭제 시 운영 내용이 사라진다.
- 관리 페이지에 서버 인증과 역할 권한이 없다.
- 댓글 숨김·복구, 크루 등록, 인증 승인·수정 기능이 아직 Hello 2027 관리 화면에 없다.

공개 페이지 UI는 배포 후보 수준이지만, 운영 데이터와 관리자 기능은 서버 저장소로 전환한 뒤 공개해야 한다.

## 현재 기존 데이터를 보는 경로

| 목적 | 현재 경로 | 주의점 |
| --- | --- | --- |
| 기존 참가자·러닝 기록 관리 | `/admin` | 관리자 이메일 OTP와 2시간 서명 쿠키 사용. 참가자와 기록 수정·삭제 가능 |
| 기존 공개 대시보드 | `/dashboard` | `scope=all`이 오늘까지 다시 계산되므로 시즌 종료 상태로 고정되지 않음 |
| TWTT 3기 전체 리포트 | `/dashboard/report/3th` | 2026-05-05~2026-08-12 기간을 live Supabase 원본에서 다시 계산 |
| TWTT 3기 개인 리포트 | `/dashboard/report/3th/[participantId]` | 현재 인증 없이 공개됨 |
| 승인 참가자의 본인 기록 | `/me` | 과거 조회뿐 아니라 새 기록 추가도 가능 |

중요: 기존 리포트는 “동결된 과거 결과”가 아니다. 현재 `participants.active`와 `daily_run_records`를 다시 읽으므로 참가자 비활성화, 기록 수정·삭제에 따라 과거 결과가 달라질 수 있다. 배포 전 이전 시즌을 별도 시즌으로 백필하고 최종 스냅샷을 만든 뒤 쓰기를 막아야 한다.

## 권장 최종 메뉴

기존 `/admin`의 OTP 흐름과 참가자·기록·OCR 기능을 확장해 상단에 시즌 선택기를 둔다.

- `TWTT 4기 · Hello 2027 — 진행 중`
- `TWTT 3기 · 100일 — 동결`

Hello 2027 시즌에는 다음 탭을 제공한다.

| 탭 | 운영 기능 |
| --- | --- |
| 크루 | 시즌 참가자 등록·수정·제외, 표시 순서, 캐릭터, 얼굴, 소개 제목·자기소개 및 동의 상태 |
| 인증 | 날짜·크루별 조회, 직접 입력, OCR 일괄 등록, 승인·반려·수정, 일일 합산 재계산 |
| 광고 | 최대 10개, 이미지·문구·대체 텍스트·초점 위치, 순서, 게시/중지, 웹·모바일 미리보기 |
| 응원글 | 최대 56개, 등록·수정·순서, 활성/비활성 |
| 댓글 | 공개/숨김/삭제 필터, 답글·반응 수, 숨김·복구·비식별 삭제 |
| 응원 상자 | 문구, 톤, 가중치, 게시 기간, 개봉 이력·통계 관리 |
| 이전 시즌 | 전체·개인 최종 리포트, CSV/JSON 내려받기, 읽기 전용 |
| 변경 이력 | 운영자가 바꾼 대상, 변경 전·후 값, 시각 조회 |

기존 `/admin`의 참가자 CRUD, 직접 기록 입력, OCR 일괄 등록은 재사용할 수 있다. 새로 필요한 부분은 시즌 선택, 광고, 응원글, 댓글, 시즌 동결과 변경 이력이다.

## 최소 서버 데이터 구조

기존 Supabase 테이블을 버리지 않고 다음 구조를 추가하는 방식이 가장 안전하다.

### 시즌과 권한

- `app_admins`: 관리자 auth user, `owner | operator` 역할, 활성 상태
- `seasons`: 이름, 기간, 타임존, 마감 시각, 최소 거리, `draft | active | archived`, `frozen_at`
- `season_participants`: 시즌별 참가자, 당시 표시명, 순서, 캐릭터, 얼굴, 소개 제목·자기소개, 동의 상태

현재 `participants.active`는 모든 시즌에 공통으로 영향을 주므로, 시즌 참가 상태를 `season_participants`로 분리해야 과거 리포트가 보존된다.

### 인증

- 기존 `daily_run_records`에 `season_id`, 합산 거리, 마감 전 거리, 인증 완료 여부, 확정 시각 추가
- `run_activity_entries`: 하루 여러 활동, 원본 증빙, OCR 결과, 승인 상태, 관리자 메모

한 날짜에 여러 활동이 있으면 `run_activity_entries`를 원본으로 보관하고 승인된 활동을 `daily_run_records`에 합산한다. 수동 수정 시 해당 날짜 집계를 같은 트랜잭션에서 다시 계산한다.

### 콘텐츠와 댓글

- `dashboard_ads`: 시즌, 소유 크루, 이미지 경로, 제목, 설명, 대체 텍스트, 모바일 초점, 순서, 게시 상태
- `encouragements`: 시즌, 본문, 순서, 활성 상태
- `guestbook_comments`: 시즌, 부모 댓글, 작성자 표시 방식, 표시명, 본문, 공개 상태, 게스트 토큰 해시
- `guestbook_reactions`: 댓글, 이모지, 게스트 토큰 해시; `(comment_id, guest_token_hash, emoji)` 고유

광고 10개, 응원글 56개, 댓글 150자 제한은 클라이언트뿐 아니라 API와 DB 제약에서도 다시 검사한다.

### 오늘의 응원 상자

- `gift_box_prizes`: 시즌별 응원 문구, 톤, 가중치, 활성 기간
- `daily_gift_claims`: 시즌 참가자·인증일별 1회 개봉 결과와 당시 문구 스냅샷

상자는 승인된 로그인 참가자의 공식 일일 인증 완료를 서버에서 확인한 뒤 지급한다. 공개 크루 카드나 브라우저 IndexedDB만으로 지급하지 않는다. 상세 흐름과 API·보안 기준은 [TWTT 4기 오늘의 응원 상자 기획](./hello-2027-daily-gift-box-plan.md)을 따른다.

### 보존과 감사

- `season_snapshots`: 최종 JSON, 레코드 수, SHA-256, 생성자·생성 시각
- `admin_audit_logs`: 운영자, 동작, 대상, 변경 전·후 값, 요청 ID

동결된 시즌의 snapshot과 audit log는 append-only로 두고 일반 update/delete를 허용하지 않는다.

## 이전 시즌 안전 전환 순서

1. Supabase DB 백업과 private Storage의 `photos`, `snasa-gallery` 객체 목록·파일 백업을 만든다.
2. 현재 참가자 수, 기록 수, 날짜별 인증 수, 거리·시간 합계를 기준값으로 저장한다.
3. `seasons`에 TWTT 3기와 Hello 2027을 생성한다.
4. 기존 참가자를 TWTT 3기 `season_participants`로 복제하고 기존 기록·배치·뱃지에 3기 `season_id`를 백필한다.
5. 백필 전후 참가자·기록·거리·시간 합계를 대조한다.
6. 현재 3기 전체·개인 리포트를 `season_snapshots`에 저장하고 해시를 기록한다.
7. 3기를 `archived`로 전환하고 DB trigger와 API 양쪽에서 수정·삭제를 차단한다.
8. 기존 공개 리포트는 관리자 전용 `/admin/seasons/[seasonId]/report`로 옮기거나 별도 공개 정책을 확정한다.
9. PoC의 기본 광고·응원글을 Hello 2027 seed로 넣는다.
10. 현재 브라우저 IndexedDB에만 있는 사용자 추가 광고·얼굴·댓글은 내보내기 후 서버로 가져온다. 현재 자동 이관 기능은 없다.

관리자 auth user UUID는 삭제하거나 교체하면 안 된다. 현재 스키마의 cascade 관계 때문에 관리자 계정 삭제가 참가자·기록 삭제로 이어질 수 있다.

## 보안 필수 조건

- `ADMIN_SESSION_SECRET`을 필수 환경변수로 만들고 service-role key fallback을 제거한다.
- 소스의 하드코딩 관리자 이메일 대신 `app_admins`에서 최종 권한을 확인한다.
- 가능하면 OTP에 TOTP 또는 Passkey MFA를 추가한다.
- service-role key는 서버에서만 사용하고 브라우저 번들에는 절대 포함하지 않는다.
- 익명 사용자가 Supabase에 직접 insert하지 못하게 하고 댓글·반응은 Next API만 통과시킨다.
- 댓글·반응 API에 동일 출처 검사, 지속형 rate limit, 스팸 방지, 150자 서버 검증을 적용한다.
- 업로드는 MIME 문자열만 믿지 않고 magic bytes 확인, 실제 디코딩, 재인코딩, EXIF 제거를 서버에서 수행한다.
- 얼굴·광고·인증 증빙은 용도별 private bucket에 저장하고 공개 화면에는 허용한 변환본만 제공한다.
- 동결 시즌은 service role도 우회하지 못하도록 PostgreSQL trigger에서 쓰기를 막는다.
- 공개 DTO에서는 증빙 원본, 정확한 활동 시각, OCR 원문, 관리자 메모를 제외한다.

로그인 없이 쓰는 “실명”은 인증된 이름이 아니라 사용자가 입력한 표시명이다. 화면과 운영 정책에서 실제 신원 인증으로 오해하게 표시하면 안 된다.

## 배포 승인 게이트

다음 항목이 모두 끝나기 전에는 개발 전용 `notFound()` 가드를 제거하지 않는다.

- 이전 시즌 백업·백필·합계 대조·snapshot·동결 완료
- 공개 Hello 2027 서버 조회 API 연결
- 관리자 인증과 `app_admins` 역할 확인 연결
- 크루·인증·광고·응원글·댓글 관리 탭 연결
- 응원 상자 지급·중복 방지·관리 기능 연결
- 댓글·반응·업로드의 서버 검증과 지속형 rate limit 적용
- production 환경변수와 private Storage 정책 검증
- 웹·모바일 접근성, 성능, 오류 상태, 빈 데이터 상태 검증
- 롤백 절차와 DB/Storage 백업 복원 테스트 완료

현재 단계의 올바른 다음 작업은 “PoC를 바로 공개”하는 것이 아니라, 위 데이터 구조와 관리자 API를 먼저 구현한 뒤 동일 UI를 서버 데이터에 연결하는 것이다.
